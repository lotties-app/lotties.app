# Lotties — Spec

Open-source (AGPL-3.0) PWA. Parents log baby events, share a baby with a co-parent, and get explainable behavior predictions. Reference app: Napper; this one adds what Napper lacks.

## Goals
- Fast one-tap logging, works offline, installable.
- Feeding has start AND end (duration); bath, tummy time, medication (pick from catalog), belly pain are first-class.
- Parents create custom event types (suggested templates provided).
- Multiple parents per baby; multiple babies per parent.
- Predictions: next sleep / next feed / typical durations, shown with the reasoning.

## Non-goals (MVP)
SSR, native apps, ML models, pro/paid tiers, growth charts. (Pediatrician sharing: step 1, read access with notes and consultation measurements, is implemented as the Doctor role: docs/design/16-doctor-access.md.)

## Stack
- Web: React 19 + TypeScript + MUI, Vite SPA, `vite-plugin-pwa`, TanStack Query, Dexie (IndexedDB), `oidc-client-ts`. Tests: Vitest + Testing Library.
- API: .NET 8 Web API, layered (Domain / Application / Infrastructure / Api), EF Core + Npgsql, xUnit. Tests: unit + Testcontainers integration.
- DB: PostgreSQL 16.
- Auth: generic OIDC (JWT bearer). Default provider Auth0; Keycloak/Authentik work via config only (`Authority`, `Audience`).
- Deploy: `docker-compose` (postgres + api + web via nginx).

## Domain model
- `User` (external OIDC issuer + subject id, unique together; display name).
- `Baby` (name, birth date). `BabyMember` (user, baby, role Owner|Parent|Caregiver|Viewer|Doctor; see "Roles and permissions"). `Invite` (token, baby, role, expiry).
- `ProfessionalProfile` (one per user, self-declared: kind `doctor`, display name, specialty?, registration number?, `verified` always false in v1), `BabyNote` (per baby, synced like appointments, soft deleted: author, kind note|recommendation, visibility shared|private, body), `AccessLogEntry` (per baby, append only: who, role, when; a Doctor's data loads, hourly). See "Doctor access".
- `EventType` (baby-scoped or built-in template): key, name, icon, color, `hasDuration`, `fields` (JSON schema-lite: text/number/select/bool). Built-ins: feeding (breast/bottle/solid, amount, side), sleep, diaper, bath, tummy_time, medication, belly_pain (intensity 1-5), breast_pump, nasal_suction (tool, saline), belly_massage (reason, helped), fussy ("Fussy / crying": intensity, what_helped), plus custom.
- `Event`: id (client-generated GUID), baby, type, `startedAt`, `endedAt?` (null = running), `payload` JSONB, notes, createdBy, `updatedAt` (server receive time, sync cursor), `clientUpdatedAt` (client edit time, decides conflicts), `deletedAt?` (soft delete for sync).
- `Medication` (baby-scoped catalog): name, default dose/unit, notes, `isUsual`, optional `productId` (link to the shared catalog). Medication event payload = `{medications: [{medicationId, name, dose?, prescriptionId?, kgUsed?, override?}]}` selected by the parent (`name` is a copy).
- Shared catalog (instance-wide): `Substance` (curated generic names en/pt-BR, plus the ones the official list names), `Product` (brand/presentation, community-added, seeded, `official` from ANVISA's registered medicines or `curated` from a small unreviewed curated list, both imported by an admin tool: docs/design/13-anvisa-catalog.md) with its substances. `Prescription` (per baby, synced like events): what the doctor prescribed for one medication; the medication status is computed, not stored. See "Medications: catalog, prescriptions, status".
- `Formula` (per baby, synced like prescriptions; docs/design/14-formulas.md): name, brand?, stage?, notes?, startedOn?, `isCurrent` (at most one per baby), `archived` (never deleted: bottles name it). A bottle of formula may name it in its payload (`formula_id` + the name snapshot `formula_name`). See "Formulas".
- `Appointment` (per baby, synced like formulas; docs/design/15-appointments.md): title, type (consultation|vaccine|exam|other), `startsAt` (UTC), durationMinutes?, location?, doctorName?, notes?, outcome?, status (upcoming|done|cancelled; `cancelled` is the soft delete, `done` only once started), reminder offsets (1 week, 1 day, 2 hours, 30 min). See "Appointments".
- Predictions are computed, not stored.

- Events: `GET /babies/{id}/events?since=<updatedAt>` (delta), `PUT /babies/{id}/events/{eventId}` (idempotent upsert), `DELETE` (soft).
- `GET /babies/{id}/predictions`.
- Push notifications: `/push/config`, `/push/subscriptions`, `/push/settings`, `/push/preferences`, `/push/test`, `PUT /babies/{id}/notification-preferences`, anonymous `POST /push/deliveries/{deliveryId}/actions` (see "Push notifications").

- Authorization: every route checks `BabyMember`; who may call each route is in "Roles and permissions" (Viewer is read-only, a Caregiver logs events and changes only their own).

## Offline sync
Client writes to Dexie first, queues mutations, replays via idempotent PUT; pulls delta with `since`. Conflict rule: last write wins by the client edit time (`clientUpdatedAt`, bounded to the server clock + 5 min); the server `updatedAt` (receipt time) only orders the delta pull. Running timers (events with null `endedAt`) are plain events.

### Events sync contract (implemented, task 6)
Base `/api/v1/babies/{babyId}`; JSON camelCase; timestamps ISO-8601, returned in UTC with microsecond precision. `EventDto` = `{id, babyId, typeId, startedAt, endedAt|null, payload (JSON object), notes|null, createdBy, createdAt, updatedAt, clientUpdatedAt, deletedAt|null}`: `updatedAt` = server receive time of the last change (the delta cursor), `clientUpdatedAt` = client edit time of the last applied change (migration `EventClientUpdatedAt` backfilled existing rows with `updatedAt`). Errors are RFC 7807 `application/problem+json` with extensions `code` (stable domain code) and, for validation, `field`.
- `PUT /events/{eventId}` (Owner/Parent/Caregiver; a Caregiver changes only an event they logged, and may stop, pause or resume someone else's running one, see "Roles and permissions"). Body `{typeId, startedAt, endedAt?, payload?, notes?, updatedAt?}`. Creates (201 + `Location`) or edits (200); returns the stored `EventDto`. Server stamps `updatedAt` on receipt of every applied change. Optional `updatedAt` = client edit time: bounded first (more than 5 minutes ahead of the server clock = server now; absent = server now), it is stored as `clientUpdatedAt` on create and on every applied edit. Conflict rule: incoming bounded `updatedAt` strictly older than the stored `clientUpdatedAt` = ignored (200, stored copy returned); equal or newer = applied. Example: a create received at 12:00 with client `updatedAt` 10:00 stores `clientUpdatedAt` 10:00, so a later stop with client `updatedAt` 10:15 is applied. Replaying the same body returns the same representation (unchanged details change nothing, neither `updatedAt` nor `clientUpdatedAt`; payload compared as JSON values). A soft-deleted event stays deleted: PUT is a no-op returning the deleted copy (200). The type must be built-in or the baby's own (else 422 `event_type_not_available`); an id that belongs to another baby is 409 `event_baby_mismatch`; invalid input (notes > 2000 or with NUL characters, payload not an object or > 16 KiB, payload strings/member names with NUL or invalid UTF-16, payload numbers longer than 64 characters or with an exponent beyond ±1000, end before start, malformed JSON) is 400.
- Payload field rules (400 `validation_failed`, `field` = the field key): the payload is checked against the type's field definitions (built-in and custom types alike). A member that is absent or `null` has no value; members no field declares are not checked (e.g. the medication payload). Values must match the kind (text = string, number = JSON number within `min`/`max`, select = one of `options`, exact case, bool = `true`/`false`; a number field with `integer: true` takes whole numbers only). A field whose `visibleWhen` is not met (or whose controlling field is hidden itself) is hidden: sending a value for it is 400, and it is never required. A visible required field must have a value once the event is complete (an instant type, or `endedAt` set): a running timer may start without it; a required bool may be absent (= false). Checked on create, and on an edit only when the type or payload changes (compared as JSON values) or a running event is being completed, so an older event whose payload predates these rules can still have its times/notes edited when its payload is sent back unchanged. The reserved pause keys are checked at the same moments for every type, declared or not (see "Timer pauses and sleep details").
- `DELETE /events/{eventId}` (Owner/Parent/Caregiver; a Caregiver only an event they logged): soft delete, always wins (whatever the stored `clientUpdatedAt`); stamps `deletedAt` = `updatedAt` = `clientUpdatedAt` = server now; 204 (also when already deleted, unknown, or belonging to another baby, which is left untouched; a Caregiver deleting someone else's event, deleted or not, gets 403 `event_not_owned`). No tombstone is created for unknown ids.
- `GET /events?since=&after=&limit=` (any member): JSON array of `EventDto` incl. soft-deleted, ordered by `(updatedAt, id)` asc. `since` is inclusive (`updatedAt >= since`; boundary rows may repeat). Page size `limit` 1-500 (default 500). When more rows follow, header `X-Next-Cursor` (CORS-exposed) holds an opaque cursor; pass it as `after` (takes precedence over `since`) until the header is absent. The `(updatedAt, id)` keyset never skips rows that share an `updatedAt`.
- `GET /events/{eventId}` (any member): the `EventDto`, soft-deleted included; 404 `event_not_found` when unknown or of another baby.

### Babies, members, invites, event types, medications (implemented, tasks 4-5)
Base `/api/v1`; JSON camelCase; roles are strings `Owner|Parent|Caregiver|Viewer` (case-insensitive on input; stored by name, no schema change for Caregiver); errors are problem+json with `code`. Status of every code is in `Api/Errors/DomainExceptionStatusCodes`.
- Babies. `GET /babies` -> `[{id, name, birthDate (yyyy-MM-dd), role, createdAt, userId}]` (role = the caller's; `userId` (additive) = the caller's own user id, the `createdBy` of the events they log, so clients can tell their own entries apart offline; also in every other `BabyDto`). `POST /babies {name, birthDate}` -> 201, the creator is Owner; `birthDate` at most the server's UTC date + 1 day (time zones ahead of UTC), else 400. `GET /babies/{id}` (any member). `PUT /babies/{id} {name, birthDate}` (Owner). No delete in the MVP (DELETE is 405).
- Members. `GET /babies/{id}/members` (any member) -> `[{userId, displayName, role, joinedAt}]`. `PATCH /babies/{id}/members/{userId} {role}` and `DELETE /babies/{id}/members/{userId}` (Owner). `DELETE /babies/{id}/members/me` (any member leaves). Demoting or removing the last Owner is 409 `last_owner_required`; unknown member 404 `member_not_found`. `displayName` is the profile `name`, else `preferred_username`, else `nickname` (each only when it contains no `@`), else `Parent`; the email claim is never read or returned (migration `Wave2Hardening` replaced stored display names containing `@` with `Parent`).
- Concurrency: a baby and its members are one aggregate with an optimistic concurrency token (PostgreSQL `xmin`, also on invites). A member change, invite accept or baby edit that lost a race against another change of the same baby is 409 `concurrent_modification` (ext `resource`, `retryable: true`); nothing was saved and repeating the request is safe.
- Invites. `POST /babies/{id}/invites {role, expiresInDays?}` (Owner; default 7, 1-30) -> 201 `{id, babyId, role, createdBy, createdAt, expiresAt, token}`; the plain token is returned only here, 256-bit random, and only its SHA-256 (base64url) is stored. `GET /babies/{id}/invites` (Owner) -> pending (not accepted, not expired) without tokens. `DELETE /babies/{id}/invites/{inviteId}` (Owner, 204, idempotent). `POST /invites/accept {token}` (any signed-in user) -> 200 `BabyDto` of the joined baby; missing/unknown/malformed/revoked 404 `invite_not_found`, expired 410 `invite_expired`, used 409 `invite_already_accepted` (also the loser of two concurrent accepts: invites carry an optimistic concurrency token), caller already a member 409 `member_already_exists` (invite stays usable). The token travels in the body so it never appears in a URL (proxy/access logs, history); the invite link keeps it in the fragment (`/invite#token`). **Deprecated:** `POST /invites/{token}/accept` (same semantics and codes) stays until the web client has migrated, then is removed; its path contains the token, so any access log that records paths (e.g. ASP.NET Core `Microsoft.AspNetCore.Hosting` at Information, which the default `Warning` level suppresses, or a reverse proxy) would capture it. The API adds no HTTP request/body logging.
- Event types. `GET /babies/{id}/event-types` (any member): built-in templates first, then the baby's custom types: `{id, babyId|null, key, name, icon, color, hasDuration, fields:[{key, label, kind (text|number|select|bool), isRequired, options?, min?, max?, unit?, visibleWhen, hidden, integer}]}`; `visibleWhen` is `null` (always shown) or `{field, equals: [..]}`: the field is shown only while the select field `field` of the same type holds one of `equals`. `hidden` (default `false`, additive) means forms must not render the field, while its value is still validated like any other (used for timer pause keys and deprecated fields); `integer` (default `false`, additive, number fields only, else 400 field `IsInteger`) accepts whole numbers only. Both are accepted on create/update and stored only when `true`. On create/update `visibleWhen` must reference another select field of the type, list only its options (at least one, unique) and form no cycle, else 400 field `VisibleWhen`. `POST` (201; `{key, name, icon, color(#rrggbb), hasDuration, fields?}`; `icon` must be one of the names in `Domain/EventTypes/EventTypeIcons` (= `code/web/src/events/iconRegistry.ts`), else 400 field `Icon`; at most 30 fields and 50 options per select field; field keys `constructor`, `__proto__`, `prototype`, `toString`, `valueOf`, `hasOwnProperty` are reserved (400 field `Key`)), `PUT /{typeId}` (`{name, icon, color, hasDuration, fields?}`; the key is immutable), `DELETE /{typeId}` (204): Parent/Owner. Built-ins reject writes with 409 `event_type_built_in_read_only`; duplicate key (also against built-ins) 409 `event_type_key_taken`; deleting a type any event (soft-deleted included) references 409 `event_type_in_use` (no archive flag); a type of another baby is 404 `event_type_not_found`. Field keys and type keys are lower snake_case (whole string; a trailing newline is rejected, as for `#rrggbb` colors).
- Built-in fields: feeding `method` (required select breast|bottle|solid), `side` (left|right|both), `breast_left_seconds`, `breast_right_seconds` (these three visible when method = breast), `amount_ml`, `bottle_feeding_type` (formula|breast_milk; visible when method = bottle), `formula_id` and `formula_name` (hidden text, visible when `bottle_feeding_type` = formula; migration `Formulas`, seed only; see "Formulas"), `food` (text, what was eaten; visible when method = solid; feeding has a duration: nursing and a bottle run from start to end, the bottle's length being how long the baby took to drink it, while solid food is logged as an instant with end = start; older bottles (logged when a bottle was an instant) and Feed-tray bottles end when they start and show no duration) (migration `ConditionalFieldsAndBreastPump`, which also rewrites stored `FORMULA`/`BREAST_MILK` payload values to lower case, bumping `updated_at` only); breast_pump (duration; icon `opacity`) `amount_left_ml`, `amount_right_ml` (optional numbers >= 0, ml); sleep `kind` (nap|night|night_waking|bed_time|woke_up|fell_asleep; bed_time, woke_up and fell_asleep are instant markers, migrations `SleepKindBedWake`, `SleepKindFellAsleep`; `fell_asleep` is never a sleep session and a nap/night timer starting within 5 min after it inside a bed_time night is absorbed by that night, so nothing is counted twice), `mood` (deprecated free text, `hidden: true`, kept so older events stay valid and readable; replaced by `mood_on_wake`), the sleep detail fields and the pause keys (see "Timer pauses and sleep details"); diaper `content` (required select WET|DIRTY|MIXED); bath `temperature_c`; tummy_time `mood`; belly_pain `intensity` (required 1-5); nasal_suction (instant, no pause keys; icon `air`; id `4124b99c-e000-4ee0-b74a-a6579553a450`; migration `NasalSuction`) `tool` (optional select bulb|electric|mouth), `saline` (optional bool); belly_massage (duration, an optional timer like tummy_time; health category; icon `massage`; id `44540b60-eb87-470f-8a3e-08170a525538`; migration `BellyMassage`) `reason` (optional select gas|constipation|colic|other), `helped` (optional select yes|a_little|no); fussy ("Fussy / crying", pt-BR "Choro / irritação"; duration, an optional timer like tummy_time; care category, as soothing is care, not a symptom; icon `sentiment_very_dissatisfied` (Tabler `mood-cry`); colour `#81c784`; id `6191006e-8767-4cd8-882f-81898fad58d3`; migration `FussyEvent`) `intensity` (optional select mild|moderate|intense), `what_helped` (optional select feeding|rocking|pacifier|massage|sleep|other|nothing); feeding, sleep, tummy_time, breast_pump, belly_massage, fussy and bath end with the hidden pause keys `pause_count`, `paused_seconds`, `paused_at`. Seed changes ship in migrations `BuiltInFieldFixups` and `PauseAndSleepDetailFields` (seed only, stored events untouched).

### Timer pauses and sleep details (API implemented; docs/design/SYNTHESIS.md sections 6 and 7)
- Pause keys (reserved payload keys, any event type, checked whether or not the type declares them; the built-in timed types and bath declare them as `hidden` fields): `pause_count` (whole number 0-100), `paused_seconds` (whole seconds of all finished pauses, 0-86400), `paused_at` (ISO-8601 instant with `Z` or `±hh:mm`, the start of the current pause; present only while paused). Rules (400 `validation_failed`, `field` = the key): numbers out of range or not whole; `paused_at` not an instant; once the event has ended (`endedAt` set) `paused_at` must be absent (clients fold the open pause into `paused_seconds` and clear `paused_at` on resume/stop) and `paused_seconds` cannot exceed `endedAt - startedAt`. `null` = absent. A running event may hold any `paused_seconds` up to the bound.
- Effective duration = `(endedAt - startedAt) - paused_seconds`, never below 0 (Domain `EffectiveDuration`; payload read leniently by `EventPayloadFacts`: a stored value breaking the rules counts as no pause). Events without pause keys keep their plain duration. Predictions use it for every typical duration (sessions of the kind-aware running sleep, `expectedDuration`, the bed-time typical night); a running sleep's expected end adds the pauses it already had (start + typical effective duration + `paused_seconds`). Awake windows (end to next start) are unchanged; a pause never splits a session.
- Sleep detail fields (built-in sleep, all optional, `visibleWhen` `kind` in [nap, night], so not for markers or night_waking and not without a kind): `how_slept` select `in_bed|nursing|held|next_to_me|bottle|stroller|car|swing|other`, `fall_asleep` select `easy|took_long|fussy`, `time_to_fall_asleep_minutes` number 0-240 (`integer`, unit `min`), `how_woke` select `naturally|woken`, `mood_on_wake` select `good|neutral|bad`.
- Medications. `GET /babies/{id}/medications` (any member; usual first, then by name) -> `[{id, babyId, name, defaultDosage:{amount,unit}|null, notes, isUsual, productId|null, createdAt}]`. `PUT /babies/{id}/medications/{medicationId} {name?, productId?, defaultDosage?, notes?, isUsual}` (Parent/Owner, client GUID; `defaultDosage.amount` is rounded to 3 decimals and must be 0.001-9999999.999, else 400 field `Amount`; idempotent: 201 created / 200 edited; an id of another baby is 409 `medication_baby_mismatch`). `productId` links a shared catalog product: it must exist and not be merged (else 422 `invalid_product_link`, ext `productId`, `reason` `not_found`|`merged`, `mergedIntoId`), checked on create and whenever the link changes (an unchanged replay never fails); `name` may then be omitted and defaults to the product name, a given name (the baby's nickname) wins; without `productId` the name is required (400), and an omitted `productId` removes the link (full-state PUT). `DELETE` (Parent/Owner) is a hard delete, 204 and idempotent; it first soft deletes the medication's prescriptions (they appear in the prescriptions delta); events keep their own medication copy in the payload, so nothing dangles.

### Medications: catalog, prescriptions, status (API implemented, M1; design docs/design/06-medications.md)
Guardrails: the app is a log and reminder tool, never dosing advice. Doses and intervals used in calculations come only from the prescription the parent entered; "same active ingredient" is information only; the per-kg suggestion shows its inputs and is always confirmed by the parent; logging early is never blocked (the entry records `override: true`). Seeds carry generic names only, with cited sources (`code/api/src/Lotties.Infrastructure/Persistence/Seed/medication-catalog.sources.md`); no product is seeded. Brands and their active ingredients come from ANVISA's open data through the admin importer `code/api/tools/Lotties.CatalogImporter` (status `official`, source `anvisa`) and from its small curated list (status `curated`, source `curated`, not reviewed by a pharmacist); docs/design/13-anvisa-catalog.md: official registration data, not reviewed by a pharmacist, never a substitution table. An ingredient is never inferred from a name or another product: a product whose records list none has no substances, and a name used by products with different ingredient sets is split into variants whose names carry their ingredients (`ambiguousName` = the shared name).
- Shared catalog, any authenticated user (no baby membership), instance-wide. `GET /catalog/substances?q=` -> `[{id, key, nameEn, namePtBr, synonyms[]}]` (all, by English name, without `q`; else the matches, best first). `GET /catalog/products?q=&limit=` (`q` at most 100 characters with at least 2 letters/digits, `limit` 1-20, default 10; else 400 `validation_failed`) -> `[{product: ProductDto, matchedBy: "name"|"alias"|"substance", distance, sameActiveIngredient: [{id, name, form, country, status}]}]`. `ProductDto` = `{id, name, form: "drops"|"syrup"|"tablet"|"powder"|"spray"|"ointment"|"suppository"|"inhaler"|"other", country (ISO alpha-2), status: "seed"|"community"|"verified"|"official"|"curated", mergedIntoId|null, substances: [{substanceId, key, nameEn, namePtBr, strength: {amount, unit, perAmount|null, perUnit|null}|null}], createdAt, source|null, presentation|null, inactive, ambiguousName|null}` (the creator is never exposed; `source`, `presentation`, `inactive` and `ambiguousName` are additive: `source` = `anvisa` for official and `curated` for curated products, `presentation` = dosage text the official name carried, e.g. `0,9%`, `inactive` = the product left its source, `ambiguousName` = the source name this product shares with products of other ingredients, e.g. `Sorine`). Search never offers inactive products (they stay readable by id, so linked medications keep their details). Substance matching: typo matches count only when no substance name matched exactly or by prefix (so `simeticona` does not also list dimeticona products). Every variant of an ambiguous name follows the first result matched by name or alias (ingredient matches are not expanded), so the list may exceed `limit`. `sameActiveIngredient`: other active, non-merged products with exactly the same substance set, official first, then curated, then the rest, by name, one per name (the same brand in another form is not listed), at most 10. `GET /catalog/substances/{substanceId}/products?offset=&limit=` (`offset` 0-100000, default 0; `limit` 1-50, default 20; else 400 `validation_failed`) -> `{substance: SubstanceResponse, total, offset, limit, items: [ProductDto]}`: the active, non-merged products containing the substance (combinations included), official first, then curated, then the rest, by name; unknown substance -> 404 `substance_not_found`; information only. `GET /catalog/products/{id}` -> `ProductDto` (merged ones included) or 404 `product_not_found`. `POST /catalog/products {name, form, country, substances?: [{substanceId, strength?}]}` -> 201 `ProductDto` (status `community`, `Location` header); when a non-merged product with the same normalized name, form and country exists -> 409 `product_exists` with extension `product` (the existing `ProductDto`; also for the loser of a concurrent create). Name: trimmed, inner whitespace collapsed, no control characters, 1-100 characters with at least 2 letters/digits; `form` and `country` required; substances from the curated list only (else 422 `substance_not_found`, ext `substanceIds`), each once, at most 10; strength amounts 0.001-9999999.999 (3 decimals), units 1-20 (400 fields `strength.*`). Rate limit `RequestLimits:CatalogWritePermitsPerMinute` (default 10 per user and minute; 429 `rate_limited`). No edit, delete, merge or verify endpoints: they need an admin role (not implemented); `Product.MergeInto`, `mergedIntoId` and `status` exist for it.
- Matching (Domain `ProductNames`, `ProductSearch`; reuses the importer's normalisation and typo tolerance): key = lower case, no diacritics, letters and digits only, repeated letters collapsed (`"Fly-Gass"` -> `flygas`; digits never collapse). Rank: equal key (0), the query is a prefix of the name (1), typo within the importer tolerance (2; keys up to 3 characters exact, up to 7 one edit, longer two; `distance` = edits), product containing a substance whose key, en/pt-BR name or synonym matches the query the same way (3); then by distance and name. A merged product's name matches as `alias` and returns its target. Candidates are loaded with plain predicates (key prefix; or key length within ±2 and the same first or last character), at most 200 per query, so no trigram extension is needed. `sameActiveIngredient` = other non-merged products with exactly the same, non-empty substance set (at most 10, by name).
- Prescriptions `/babies/{id}/prescriptions` (sync contract as for events). `PrescriptionDto` = `{id, babyId, medicationId, status: "active"|"stopped", kind: "scheduled"|"asNeeded", dose: {amount, unit, perKg, roundingStep|null}, timesOfDay: ["HH:mm"]|null, everyMinutes|null, dayParts: ["morning"|"afternoon"|"evening"|"night"]|null, dayPartReminders: [{part, time: "HH:mm"}]|null, minIntervalMinutes|null, maxDosesPer24h|null, indication|null, intervalGroup|null, startDate, endDate|null, prescriber|null, instructions|null, createdBy, createdAt, updatedAt, clientUpdatedAt, deletedAt|null}` (`dayParts`/`dayPartReminders` are additive: absent or `null` on older rows and clients). `GET ?since=` (any member): the baby's prescriptions with `updatedAt >= since` (all without it), soft-deleted included, ordered by `(updatedAt, id)`; no paging. `PUT /{prescriptionId}` (Parent/Owner, client GUID) body = the editable fields plus optional `updatedAt` (client edit time, bounded like events): 201 + `Location` / 200; replaying identical terms changes nothing (not even `updatedAt`); a stale client time (older than the stored `clientUpdatedAt`) is ignored (200, stored copy); a soft-deleted prescription stays deleted (200, deleted copy); an id of another baby is 409 `prescription_baby_mismatch`; a `medicationId` not in the baby's catalog is 422 `prescription_medication_not_found` (checked on create and when it changes). `DELETE /{prescriptionId}` (Parent/Owner): soft delete, always 204. Rules (400 `validation_failed`, `field` as named): `status` defaults to `active`; `kind`, `dose`, `startDate` required; `dose.amount` 0.001-9999999.999 (3 decimals), `dose.unit` 1-20 (free text); `dose.roundingStep` 0.001-1000 and only with `perKg`; counted units (`Domain/Medications/DoseUnits`: spray(s)/jato(s)/borrifada(s), puff(s)/inalação(ões), suppository/suppositories/supositório(s), application(s)/aplicação(ões), any case, with or without accents) are never per kg (field `dose.perKg`), sprays and puffs need a whole `dose.amount` and suppositories a multiple of 0.5 (half suppositories); scheduled: exactly one of `timesOfDay` (1-24 distinct `HH:mm`, stored sorted), `everyMinutes` or `dayParts` (1-4 distinct exact lower-case codes, stored in day order; an empty list is 400 `dayParts`), and no `minIntervalMinutes`/`maxDosesPer24h`; `dayPartReminders` (optional, `null` or `[]` = off) only with `dayParts` (else 400 `dayPartReminders`), each part at most once and one of the chosen parts, `time` `HH:mm` inside that part's window (night 22:00-04:59); as needed: `minIntervalMinutes` required, `maxDosesPer24h` 1-24 optional, no `timesOfDay`/`everyMinutes`/`dayParts`/`dayPartReminders`; intervals 15-10080 minutes (15 min to 7 days); `indication` <= 200 (both kinds), `intervalGroup` <= 50 (normalised: lower case, no diacritics, single spaces), `prescriber` <= 100, `instructions` <= 1000, no NUL; dates 2000-01-01..2100-12-31 with `endDate >= startDate`. Unknown `kind`/`status` strings are 400 (binding).
- Medication event payload extensions (built-in medication type only; checked on create and when an edit changes the payload or completes the event; older payloads and the Napper importer's stay valid): per entry `prescriptionId` (a GUID string naming a prescription of the same baby for the entry's `medicationId`; soft-deleted prescriptions are accepted so doses logged offline still sync), `override` (bool: logged before the allowed time), `kgUsed` (number > 0 and <= 1000); `null` means absent. Violations are 400 `validation_failed` with `field` `medications[i].prescriptionId|override|kgUsed`. Clients must push a prescription before the events that reference it.
- `GET /babies/{id}/medications/status?utcOffsetMinutes=` (any member; offset -840..840, default 0, else 400) -> `{babyId, generatedAt, utcOffsetMinutes, items: [...]}`, one item per active, non-deleted prescription, by medication name: `{prescriptionId, medicationId, medicationName, product: {id, name, substances: [{id, key, nameEn, namePtBr}]}|null, kind, dose, timesOfDay, everyMinutes, minIntervalMinutes, maxDosesPer24h, indication, intervalGroup, groupMembers: [{prescriptionId, medicationId, medicationName}], startDate, endDate, courseStarted, courseEnded, availableNow, availableAt|null, nextScheduledAt|null, overdueByMinutes|null, lastDoseAt|null, dosesLast24h, limitReached, suggestedDose: {amount, exactAmount, unit, perKgAmount, kgUsed, weightDate, stale, roundingStep|null}|null, dayParts|null, dayPartReminders|null, dayPartsStatus: {day, parts: [{part, day, start, end, state: "upcoming"|"due"|"given"|"missed", givenAt|null, doseCount, reminderAt|null}], currentPart|null, next: {same shape as a part}|null, givenCount, total, guard: "none"|"alreadyGiven"|"outsideParts"}|null}` (instants in UTC; rule fields, no prose; `dayPartsStatus` only for part-of-the-day prescriptions).
- Calculator semantics (pure Domain `MedicationStatusCalculator`, to be mirrored offline by the web): doses = entries of non-deleted built-in medication events (time = event start) of the last 9 days. A dose counts for a prescription when its entry names the prescription or its medication; scheduled slots only take entries that name no other prescription. Interval clock = the latest dose of the prescription's medication or of any other active member of its interval group; wait = the prescription's own interval (as-needed `minIntervalMinutes`, or scheduled `everyMinutes`); a times-of-day member uses the smallest interval of the other members; `availableAt` = clock + wait (may be in the past; null without dose or interval). Max per 24h counts the medication's doses in (now-24h, now]; at the limit `limitReached` and `availableAt` is at least when the oldest counted dose leaves the window. `availableNow` = the course covers local today (`startDate <= today <= endDate`, local by `utcOffsetMinutes`) and `availableAt` is absent or not after now. Times of day: slots of local yesterday, today and tomorrow inside the course dates; each slot, in time order, takes the nearest unused dose within ±90 minutes (works across midnight); `nextScheduledAt` = the earliest open slot after now; `overdueByMinutes` = whole minutes since the latest open slot at or before now that is today's or at most 90 minutes old, ignoring slots before the prescription was created. `everyMinutes`: `nextScheduledAt` = last dose + period (none before the first dose), overdue when past. `suggestedDose` (per-kg rules with a measured weight): `exactAmount` = `dose.amount` x latest weight (3 decimals), `amount` = rounded to the nearest multiple of `roundingStep` (midpoint away from zero; may be 0; equals `exactAmount` without a step), `stale` when the weight is more than 30 days older than local today. `override` does not change the computation. Part of the day (`Domain/Prescriptions/DayPartWindows`, mirrored by `code/web/src/medications/dayParts.ts`, shared vectors `code/web/src/medications/dayPartVectors.json`): fixed local windows morning 05:00-12:00, afternoon 12:00-18:00, evening 18:00-22:00, night 22:00-05:00; a routine day starts at 05:00 (the night after midnight belongs to the previous date); per chosen part of the current routine day `given` = an own dose (same rule as slots) inside `[start, end)`, else `due` while open, `upcoming` before, `missed` after (informative); a part that ended before `createdAt` without a dose is left out; `next` = the earliest due or upcoming part of today or the next routine day inside the course; `courseStarted`/`courseEnded`/`availableNow` compare the course dates with the routine day; `guard` = `alreadyGiven` when the part containing now has a dose, `outsideParts` when now is in no chosen part, `none` otherwise or outside the course (clients ask before logging and record `override`); `nextScheduledAt`/`overdueByMinutes` stay null. The offset is fixed for the request (DST changes inside the window are not modelled).

### Formulas (API implemented; docs/design/14-formulas.md)
Base `/api/v1/babies/{babyId}`; JSON camelCase; sync contract as for prescriptions (server `updatedAt` = delta cursor, client `updatedAt` stored as `clientUpdatedAt` decides conflicts).
- `GET /formulas?since=` (any member): the baby's formulas with `updatedAt >= since` (all without it), archived included, ordered by `(updatedAt, id)`; no paging. `FormulaDto` = `{id, babyId, name, brand|null, stage|null, notes|null, startedOn (yyyy-MM-dd)|null, isCurrent, archived, createdBy, createdAt, updatedAt, clientUpdatedAt}`.
- `PUT /formulas/{formulaId}` (Owner/Parent, client GUID) body `{name, brand?, stage?, notes?, startedOn?, isCurrent?, archived?, updatedAt?}` (full state; booleans default `false`): 201 + `Location` / 200; replaying identical state changes nothing (not even `updatedAt`); a stale client time (older than the stored `clientUpdatedAt`) is ignored (200, stored copy); an id of another baby is 409 `formula_baby_mismatch`. Rules (400 `validation_failed`, `field`): `name` required, trimmed, at most 60 characters; `brand` at most 60, `stage` at most 10, `notes` at most 1000 (blank = absent, no NUL); `startedOn` 2000-01-01..2100-12-31. `archived: true` stores `isCurrent: false`. No `DELETE` (405): a formula is archived, never deleted, because bottles name it.
- One current formula per baby: a PUT that makes a formula current makes every other formula of the baby not current in the same transaction (they get `updatedAt` = server now, so they appear in the delta, and `clientUpdatedAt` = the bounded client time of that PUT when it is newer than theirs, so an older offline write that would make one of them current again is stale). Enforced by the partial unique index `ux_formulas_one_current_per_baby` (`baby_id WHERE is_current`); a lost race is 409 `concurrent_modification` (`resource: "formula"`, `retryable: true`), and clients retry it.
- Feeding payload members (built-in feeding only; checked on create and when an edit changes the payload or completes the event, like every payload rule): `formula_id` (a GUID string naming a formula of the same baby, archived ones included) and `formula_name` (string, at most 60 characters: the name when the bottle was logged, so the history keeps it after a rename or an archive); both hidden fields visible only when `bottle_feeding_type` = `formula`, so sending them for breast milk or another method is 400 like any hidden field. Violations: 400 `validation_failed`, `field` `formula_id` / `formula_name`. Clients push a formula before the bottles that name it. The Napper importer writes neither; older payloads stay valid.

### Push notifications (API implemented, N4; design docs/design/09-push-notifications.md)
Self-hosted Web Push (VAPID, RFC 8291 `aes128gcm`), no third-party push vendor. Push is on only when `PUSH_VAPID_PUBLIC_KEY`, `PUSH_VAPID_PRIVATE_KEY` and `PUSH_VAPID_SUBJECT` are all set (aliases of `Push:Vapid:*`; some but not all, an invalid or mismatched pair, or a bad subject fails startup); `dotnet Lotties.Api.dll --generate-vapid-keys` prints a new pair and exits. When push is off every route below except `GET /push/config` is 409 `push_not_configured`. Base `/api/v1`, JSON camelCase, errors problem+json with `code`. Endpoints, keys, tokens and payloads are never returned or logged.
- `GET /push/config` (any signed-in user) -> `{enabled, publicKey|null}` (base64url uncompressed P-256; the web hides the feature when `enabled` is false).
- `POST /push/subscriptions` (any user) body = `PushSubscription.toJSON()` plus fields: `{endpoint, expirationTime|null (ms since epoch), keys: {p256dh, auth}, locale, deviceLabel?}`. Upsert by endpoint (SHA-256): 201 new / 200 existing (keys, locale, label and `lastSeenAt` refreshed, un-revoked; an endpoint of another user is transferred to the caller and that user's pending deliveries for it are cancelled). Returns `{id, deviceLabel|null, locale, createdAt, lastSeenAt, lastSuccessAt|null}`. At most `Push:MaxSubscriptionsPerUser` (default 10) active devices: the least recently seen beyond it are revoked (`inactive`). Rules: `endpoint` an absolute `https` URL, port 443, no user info, at most 2048 characters (400 `validation_failed`, `field` `endpoint`); host on `Push:AllowedEndpointHosts` (default `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `*.push.services.mozilla.com`, `web.push.apple.com`, `*.push.apple.com`, `*.notify.windows.com`; `*.` = any subdomain) else 422 `push_endpoint_not_allowed` (the SSRF guard, re-checked before every send); `keys.p256dh` base64url of 65 bytes starting `0x04`, `keys.auth` of 16 bytes (400, `field` `keys.p256dh`/`keys.auth`); `locale` `en`|`pt-BR`, anything else stored as `en`; `deviceLabel` at most 60 characters, no NUL.
- `POST /push/subscriptions/revoke {endpoint}` (any user) -> 204 always; revokes the caller's device with that endpoint (unknown or another user's endpoint is a no-op). The endpoint travels in the body so it never appears in a URL.
- `GET /push/subscriptions` (any user) -> the caller's active devices (not revoked, not expired), same shape as above. `DELETE /push/subscriptions/{id}` (any user) revokes one of the caller's devices; 204, idempotent, another user's id is a no-op. Revoking cancels the device's pending deliveries.
- `GET /push/settings` / `PUT /push/settings` (any user) `{timeZone, quietHours: {enabled, start: "HH:mm", end: "HH:mm"}, quietIncludesMedicine, showNames}` (full state; PUT returns the stored state). Before the first PUT, GET returns the defaults with `timeZone: null`, quiet hours on 22:00-07:00, both flags false. `timeZone` must be a known IANA id (400 `field` `timeZone`); times must be `HH:mm` and differ (400 `field` `quietHours.start`/`quietHours.end`); `quietHours` is required. The scheduler skips users without a time zone.
- `GET /push/preferences` (any user) -> `[{babyId, canReceive, doseDue, doseLeadMinutes, napWindow, napLeadMinutes, bellyPainPattern, overtiredWarning, fussyPattern, diaperWetHeadsUp, diaperDirtyHeadsUp, appointmentReminders}]` for every baby the caller belongs to, by baby name; `canReceive` = role Owner, Parent or Caregiver; before the first PUT everything is off (dose lead 0, nap lead 10) except `appointmentReminders` (on); Viewers always get everything off.
- `PUT /babies/{babyId}/notification-preferences {doseDue?, doseLeadMinutes?, napWindow?, napLeadMinutes?, bellyPainPattern?, overtiredWarning?, fussyPattern?, diaperWetHeadsUp?, diaperDirtyHeadsUp?, appointmentReminders?}` (Owner/Parent/Caregiver, the caller's own row only) is a merge: every field is optional and a field that is absent or `null` keeps the stored value (the defaults before the first PUT), so a client that does not know a newer kind never turns it off (before 2026-10-22 an omitted `bellyPainPattern` turned it off and the first four were required). -> 200 with the stored item; Viewer or non-member 403 (Viewers never receive baby reminders); the merged `doseLeadMinutes` in 0, 5, 15 and `napLeadMinutes` in 0, 10, 20 (else 400 with that `field`). Preferences are deleted with the membership (columns `belly_pain_pattern`, migration `BellyPainPattern`; `overtired_warning` and `fussy_pattern`, migration `FussyAndOvertiredPrefs`; `diaper_wet_headsup` and `diaper_dirty_headsup`, migration `DiaperHeadsUpPrefs`; all NOT NULL default false; `appointment_reminders`, migration `Appointments`, NOT NULL default TRUE).
- Belly pain heads-up (`belly_pain_pattern`, docs/design/09-push-notifications.md section 2.5, docs/design/11-patterns.md): when the baby's belly pain pattern exists (read in the recipient's time zone), one per baby and local day at window start - 30 min, unless a belly pain or belly massage was logged from window start - 45 min on; dropped in quiet hours (not a medicine); key `belly:{baby}:{local date yyyyMMdd}`; expires 15 min after the window ends.
- Overtired heads-up (`overtired_warning`, docs/design/09-push-notifications.md section 2.6, docs/design/11-patterns.md section 6): when the baby's wake window exists (read in the recipient's time zone) and she is awake (no sleep running, no night waking since the last sleep), one per awake stretch at `awake since + limit - 15 min`, sent for 15 min while before `limit + 30 min`; a sleep that starts ends the stretch; dropped in quiet hours; key `overtired:{baby}:{awake since utc yyyyMMddHHmm}`; expires 30 min after the limit.
- Fussy pattern heads-up (`fussy_pattern`, section 2.7, docs/design/11-patterns.md section 7): the belly pain rules over the baby's `fussy` pattern (a fussy spell logged from window start - 45 min on handles the day); key `fussy:{baby}:{local date yyyyMMdd}`.
- Diaper heads-ups (`diaper_wet_headsup`, `diaper_dirty_headsup`, docs/design/09-push-notifications.md section 2.8, docs/design/11-patterns.md section 8): from the baby's diaper predictions (see "Predictions"). Wet: one at the expected wet diaper - 10 min, keyed by the latest wet diaper (`wet:{baby}:{anchor utc yyyyMMddHHmm}`). Dirty: at the end of the latest feed + the lower lag when the lag after feeds applies (feed ended at most 3 h ago, no dirty diaper since), else at the gap-based expected time - 5 min (`dirty:{baby}:{anchor utc yyyyMMddHHmm}`, the feed end or the latest dirty diaper). Sent for 15 min, not after the expected time + 30 min (the expiry); dropped in quiet hours; at most 3 per kind, baby and recipient per local day (sent or pending ones count; failed, expired, gone and cancelled do not) and never two of either kind within 60 min (skip reasons `daily_cap`, `spacing`).
- `POST /push/test {endpoint?}` (any user) -> 200 `{results: [{subscriptionId, status: "sent"|"gone"|"failed"}]}`: sends a `test` notification synchronously (10 s send timeout per device) to the caller's active device with that endpoint, or to all of them without it (no matching device = empty results). Each send is logged as a delivery; 404/410 revokes the device (`gone`), 400/403 revokes it as `invalid`, other failures count towards the 10-consecutive-failures revocation.
- `POST /push/deliveries/{deliveryId}/actions {action: "snooze"|"dismiss", token}` (anonymous: the per-delivery action token from the payload is the credential, so the service worker can call it without an access token; the app uses the same route from the deep link) -> 204. Unknown delivery, wrong or missing token, a `test` delivery, or more than 12 h after the delivery's due time: 404 `notification_action_not_found` (one code for every case). Unknown `action` 400 `field` `action`. Snooze is per user (never silences a co-parent): 30 minutes, at most 3 times per reminder, the fourth 409 `snooze_limit_reached`; dismiss ("Stop reminders for this dose") cancels the user's pending snooze re-sends of that reminder.
- Appointment reminders (`appointment_reminder`, docs/design/09-push-notifications.md section 2.9, docs/design/15-appointments.md): on by default per member and baby (a member without stored preferences is a candidate while the baby has an upcoming appointment within a week), for Owners, Parents and Caregivers with an opted-in device. For every upcoming appointment that has not started and each offset: at `start - offset`; inside the member's quiet hours delayed to their end when that is still before the start, else skipped; an offset already past when the appointment was last changed is skipped; of the offsets due at once only the latest goes. Key `appt:{appointment}:{start utc yyyyMMddHHmm}:{offset}` (moving the start plans new reminders); stale cutoff 30 min; TTL until the start; urgency normal. Done and cancelled appointments never remind.
- Payload (encrypted; the service worker renders the text from its own catalog): `{v: 1, id, kind: "dose_due"|"nap_window"|"belly_pain_pattern"|"overtired_warning"|"fussy_pattern"|"diaper_wet_headsup"|"diaper_dirty_headsup"|"appointment_reminder"|"test", babyId?, rxId?, apptId?, offset?, at (UTC instant), lang, token?, names?: {baby, medication?}}`; `apptId` and `offset` (minutes) only for appointment reminders, whose `at` is the start (never the title, doctor or notes); `names` only with `showNames` on, never a dose amount; `belly_pain_pattern` and `fussy_pattern` carry codes only (`at` = the usual window's start, no symptom detail), `overtired_warning` too (`at` = when the awake stretch reaches the usual limit), and the diaper kinds (`at` = the expected diaper, never the content); `test` carries `{v, id, kind, at, lang}` only. Headers `TTL` (dose 90 min, nap up to 60 min, belly pain and fussy until 15 min after the window, overtired until 30 min after the limit, diapers until 30 min after the expected time, appointments until the start, test 5 min), `Urgency` (`high` for doses), `Topic` from the base key.
- Rate limits (fixed one-minute window, section `RequestLimits`, non-positive fails startup): `PushWritePermitsPerMinute` 30 per user (subscribe, revoke, delete, PUT settings, PUT baby preferences), `PushTestPermitsPerMinute` 3 per user, `PushActionPermitsPerMinute` 20 per remote address (the anonymous action route); the global 300 per user still applies. Over the limit: 429 `rate_limited`.
- Error codes: `push_not_configured` 409, `push_endpoint_not_allowed` 422, `notification_action_not_found` 404, `snooze_limit_reached` 409.

### Input and request limits (API)
- Free text (names, notes, labels, options, units, display names) is trimmed, bounded by its column length and must not contain NUL (`U+0000`): 400 `validation_failed` with `field`. Values the database could not store are always a 400 from the domain, never a 500.
- Request body: at most 1 MiB, the two Napper import endpoints 6 MiB (each CSV is still limited to 5 MB by the import: 413 `import_file_too_large`). Larger bodies are 413 `request_body_too_large` (ext `maxBytes`).
- Request timeout: 30 s, imports 120 s; a timed-out request is 504.
- Rate limit, fixed one-minute window per user (`sub`; anonymous per remote address): 300 requests, and additionally 10 import requests (preview + import), 10 catalog product creations and the push limits (see "Push notifications"). Over the limit: 429 `rate_limited` with a `Retry-After` header (seconds). `/health` is not limited.
- All configurable in section `RequestLimits` (`MaxRequestBodyBytes`, `ImportMaxRequestBodyBytes`, `RequestTimeoutSeconds`, `ImportRequestTimeoutSeconds`, `PermitsPerMinute`, `ImportPermitsPerMinute`, `CatalogWritePermitsPerMinute`, `PushWritePermitsPerMinute`, `PushTestPermitsPerMinute`, `PushActionPermitsPerMinute`; env e.g. `RequestLimits__PermitsPerMinute`); non-positive values fail startup.
- A database error on insert that is not a unique violation (a lost idempotent race) is logged and surfaces as 500; unique violations keep their idempotent outcome (reload the winner, 409 `event_type_key_taken`, 409 `import_conflict`).

## Predictions (heuristic v1.1)
Per baby + event type: take last 14 days, compute median interval between starts and median duration; weight recent days higher; for sleep/feed bucket by age band (0-3m, 3-6m, 6-12m, 12m+) when enough data, else fall back to all data. Output: expected next start window, confidence (by sample count), and a human-readable reason. Pure function in Domain; unit-tested.
- Sleep is predicted from sleep sessions built from the payload `kind`: `nap`, `night` and sleeps without a kind are sessions as logged; `bed_time` -> the next `woke_up` (within 16 h, no other `bed_time` between) is a night session, a trailing `bed_time` within 16 h of now is a night in progress, unpaired markers are ignored; `night_waking` episodes are not sleep and never shorten awake windows.
- v1.1 changes, from the backtest in `docs/ml/BENCHMARK.md` (Recommendation 1; wake-up MAE 92 -> 43 min in test, 124 -> 74 in validation; bed-time clocks MAE 45 / 96 min):
  - Kind-aware running sleep: while a sleep runs, its expected end (start + typical duration, never earlier than now; the next sleep is measured from it) uses only finished sessions of the same kind: nights (logged `night` timers and `bed_time` nights) for a night, every other session (`nap`, no kind, unknown kind) for a nap, as the web's `sleepSessionKind`. Within that kind the usual narrowing applies: current age band and the day/night phase of the sleep's start, each only with at least 5 samples; then all sessions of that kind; fewer than 3 samples = no typical duration (the next start is then measured from now). v1 took every session of the same phase, so a nap after 19:00 was expected to last a night and a bed time before 19:00 a nap. `expectedDuration` of a prediction (the typical length of the next sleep, measured at its expected start) keeps the v1 rule (all sessions, narrowed by phase).
  - Bed time: the next night's start from the last 14 bed times in the look-back window (starts of night sessions, one per evening: the earliest), with local clock times by the request's `utcOffsetMinutes` on an evening day that starts at 04:00 (so 00:30 is a late bed time). Only the clocks later than now's clock are kept; the window is their q25 / median / q75 (unweighted, linear interpolation, rounded to the minute) placed on the current evening; the expected duration is the typical night (night sessions only, as above). Returned only with at least 5 bed times, at least one clock still later than now, no night in progress and no night already started this evening; otherwise `null`. Confidence uses the same thresholds as other predictions on the number of later clocks.
  - The q25-q75 window of next-start predictions is unchanged (47-50 % coverage for a nominal 50 %).
- Durations are effective durations (pauses excluded, see "Timer pauses and sleep details"); identical to v1.1 for events without pause keys, so `engineVersion` stays `heuristic-1.1`.
- Recurring time-of-day patterns (additive, docs/design/11-patterns.md): optional query `timeZone` (IANA id; an unknown id falls back to `utcOffsetMinutes`) places events in local time with the offset of each instant (daylight saving applied). Response `patterns: [{typeKey: "belly_pain"|"fussy", typicalClock, windowStart, windowEnd ("HH:mm" local; the window crosses midnight when the end is earlier), windowMinutes, spreadMinutes, confidence: "Low"|"Medium"|"High", eventDayCount, recentDayCount, timeZone|null, days: [{date: "yyyy-MM-dd", times: ["HH:mm"]}] (oldest first), rule: {lookBackDays, recentDays, minimumRecentDays, maximumSpreadMinutes, minimumCoveragePercent, leadMinutes}}]` (empty without a pattern). Detector rules: 14 local days; one sample per day (events within 12 h of the usual time are one day); circular mean and standard deviation, spread at most 45 min; window = mean ± max(30 min, spread), at most 3 h; at least 60 % of the days with an event inside the window and at least 4 of the last 7 days. The web shows the Now suggestion from it (cached with the predictions for offline use) and decides "already logged" and "Not today" locally. The `fussy` entry uses the same detector and rules over fussy spells (a fussy spell handles the window).
- Wake window (additive, the overtired heads-up, docs/design/11-patterns.md section 6): `wakeWindow: {limitMinutes, sampleCount, awakeSince (UTC)|null, awakeMinutes|null, timeZone|null, stretches: [{start, end (UTC), minutes}] (oldest first), rule: {lookBackDays: 14, dayStartsAt: "05:00", dayEndsAt: "18:00", percentile: 75, minimumStretches: 5, leadMinutes: 15, graceMinutes: 30}}|null`. Pure Domain rules (`WakeWindows`): sleep sessions as for the nap window; an awake stretch runs from the latest end of the sessions so far to the next session's start; only finished stretches that started in the last 14 days between 05:00 (inclusive) and 18:00 (exclusive) local time (zone per instant, so daylight saving is applied; lengths are elapsed time); stretches under 1 min or over 3 times the plain median are dropped; with fewer than 5 left `wakeWindow` is `null` (nothing is guessed); `limitMinutes` = the 75th percentile (linear interpolation), to the minute. `awakeSince` = the latest sleep end (session or `woke_up` marker); `null` while a sleep runs, after a newer lone `fell_asleep` marker, or when a night waking ended at or after it. The web shows the Now card from `limitMinutes` and measures the current stretch from local events (offline-safe).
- Diapers (additive, docs/design/11-patterns.md section 8): `diaper: {wet: {anchorAt, nextStart: {earliest, expected, latest}, lowerGapMinutes, medianGapMinutes, upperGapMinutes, eventCount, gapCount, confidence, trend: {last24Hours, usualPer24Hours, droppedSharply}|null}|null, dirty: {lastDirtyAt|null, gap: (same shape, trend null)|null, afterFeed: {lowerLagMinutes, medianLagMinutes, upperLagMinutes, pairCount, confidence, latestFeedEndedAt|null}|null}|null, rule: {wetLookBackDays: 7, minimumWetEvents: 8, dirtyLookBackDays: 14, minimumDirtyEvents: 5, lowerPercentile: 25, upperPercentile: 75, feedWindowMinutes: 180, minimumFeedPairs: 5, maximumLagSpreadMinutes: 40, leadMinutes: 20, graceMinutes: 40}}`. Pure Domain rules (`DiaperPredictions`): a wet diaper is `content` `WET` or `MIXED`, a dirty one `DIRTY` or `MIXED`; gaps between consecutive diapers of the kind (elapsed time, so daylight saving changes do not matter) without duplicates (under 1 min) and outliers (over 3 times the plain median), at least 3 left; wet needs at least 8 wet diapers in the last 7 days, the dirty gap at least 5 dirty ones in the last 14 days; expected = latest diaper of the kind + recency-weighted median gap, window = weighted 25th-75th percentile gaps. After feeds: the lag from the end of the latest feed that ended at most 3 h before a dirty diaper (the first dirty one after it), at least 5 such pairs in 14 days and the interpolated 25th-75th percentile lags at most 40 min apart. A part whose gate fails is `null` (nothing is guessed). Confidence from the number of gaps (pairs) and the window's width. `trend` (wet only): the last 24 h against the usual count per 24 h before (at least 2 days of history); `droppedSharply` = at most half of a usual count of at least 4. The web re-anchors at its latest local diaper or finished feed (offline-safe) and shows the Now cards from 20 min before until 40 min after the expected time.
- Response `GET /babies/{id}/predictions?utcOffsetMinutes=&timeZone=` (additive in v1.1: `engineVersion`, `bedTime`; later `patterns`, `wakeWindow` and `diaper`, above; existing fields unchanged): `{babyId, generatedAt, engineVersion: "heuristic-1.1", predictions: [{typeKey, nextStart: {earliest, expected, latest}, expectedDuration: {minutes, sampleCount}|null, confidence: "Low"|"Medium"|"High", sampleCount, reason, basis: {kind: "StartInterval"|"AwakeWindow", medianGapMinutes, lookBackDays, ageBand|null, dayPhase|null, assumesEventInProgressEnds}}], insufficientData: [{typeKey, sampleCount, requiredSamples, reason}], bedTime: {typeKey: "sleep", kind: "night", nextStart, expectedDuration|null, confidence, sampleCount, reason, basis: {kind: "BedTimeClock", sampleCount, recentBedTimeCount, lookBackDays, medianClock: "HH:mm"}}|null}`. Instants are UTC, lengths whole minutes; `bedTime` is kept out of `predictions` so the list still has one entry per type (the `sleep` entry stays the next sleep after the last wake). `reason` is English; clients build their own text from `basis` (`medianClock` is the local time by `utcOffsetMinutes`).

## Napper import (from real exports)
Parents can import a Napper CSV export. Findings from a real export (1248 events, 2026-08-31 to 2026-10-20, offset -03:00):
- Logs CSV columns: `start,end,category,overallHappiness,babyMoodOnWakeUp,babyMoodOnSleep,diaperWeight,diaperContent,breastLeftSeconds,breastRightSeconds,amountPumpedLeft,amountPumpedRight,feedingAmount,temperature,bottleFeedingType,comment,numberOfPauses,pausedMinutes,units,howBabySlept,howBabyWoke,timeToFallAsleep,createdAt,updatedAt`. Timestamps are ISO-8601 with offset; instant events have `start == end`.
- Categories seen: `BOTTLE`, `CHANGED_DIAPER`, `NAP`, `NIGHT_WAKING`, `MEDICINE`, `BED_TIME`, `WOKE_UP`, `NURSING`. Map to built-in types: BOTTLE->feeding(bottle: `feedingAmount` ml, `bottleFeedingType` FORMULA|BREAST_MILK stored as formula|breast_milk), PUMPING/BREAST_PUMP->breast_pump (`amountPumpedLeft`/`amountPumpedRight` ml), NURSING->feeding(breast: left/right seconds, pauses), CHANGED_DIAPER->diaper (`diaperContent` WET|DIRTY|MIXED), NAP/NIGHT_WAKING/BED_TIME/WOKE_UP->sleep family (`howBabySlept`, `howBabyWoke`, moods), MEDICINE->medication.
- Napper medication is free text in `comment` and often lists several (e.g. "Colidis e Puravit", typos like "Flagas"/"Flygas"). Confirms the need for a medication catalog with multi-select; the importer maps comments to catalog entries via a reviewable mapping step (user confirms unmatched names), never silently.
- Measurements CSV: `dateOfMeasurement,weightKg,heightCm,headCircumferenceCm` (cm columns may be empty). Add a `Measurement` entity (baby, date, weightKg?, heightCm?, headCircumferenceCm?) and import it; simple list/chart in UI. This promotes basic growth tracking into MVP scope.
- Import is idempotent: deterministic event ids derived from (baby, category, start, end) so re-importing does not duplicate. Duplicate files must be tolerated (the two log exports provided were byte-identical).
- Real exports contain a child's personal data: never commit them; `docs/samples/` is gitignored, tests use small synthetic fixtures with the same columns.

### Napper import API (implemented, task 17)
Two phases, both `POST`, Parent/Owner (Viewer/non-member 403, anonymous 401), JSON body (not multipart) with the CSV texts; errors are problem+json with `code` plus the extensions listed.
- Body `NapperImportRequest` = `{logsCsv?, measurementsCsv?, medicationMappings?: [{token, action: "existing"|"create"|"ignore", medicationId?, name?}], options?: {categories?: ["NAP", ...]}}`. At least one CSV (else 400 `validation_failed`). Each CSV max 5 MB UTF-8 (413 `import_file_too_large`, ext `field`, `maxBytes`) and 20000 data rows (400 `import_too_many_rows`, ext `field`, `maxRows`); the medicine rows may name at most 500 distinct medications (case/diacritics-insensitive; 400 `import_too_many_medication_names`, ext `maxNames`) and a medicine row naming one longer than 80 characters is skipped as `invalid_record`; unterminated quote, empty file or missing required column (logs: `start,end,category`; measurements: `dateOfMeasurement`) is 400 `import_invalid_file` (ext `field`). Unknown `action` is 400. `options.categories` (case-insensitive) limits the Napper categories imported; others are skipped as `excluded_category`. `options.enrichExisting` (bool, default `false`): see "Enrich existing events" below.
- CSV: RFC 4180 (quotes, `""`, embedded commas/line breaks), BOM, CRLF/LF/CR, blank lines ignored, columns found by name in any order (case-insensitive), extra columns ignored. Timestamps must be ISO-8601 with `Z` or `±hh:mm` (no offset = row skipped), stored in UTC. Numbers invariant (a lone decimal comma accepted); an unreadable `numberOfPauses`/`pausedMinutes` no longer skips the row (it becomes a skipped field). Measurement dates `yyyy-MM-dd` or an ISO timestamp (its local calendar date). `createdAt`/`updatedAt` are ignored.
- `POST /babies/{id}/import/napper/preview` -> 200 `{logs: NapperLogsSummary|null, measurements: NapperMeasurementsSummary|null, medicationSuggestions: [...], unmappedTokens: [string]}`; writes nothing. `NapperLogsSummary` = `{totalRows, toCreate, alreadyImported, skipped, from|null, to|null (UTC, span of importable rows), categories: [{category, eventTypeKey|null, total, toCreate, alreadyImported, skipped}], skippedRows: [{row, category|null, code, reason}], skippedFields: [{row, category, field, value, code, reason}]}` (`row` = 1-based data record, header not counted; `skippedFields` (additive) = detail values of importable rows, new or already imported, that could not be mapped to their payload field: `field` is the Napper column, `value` the raw text (at most 100 characters), `code` `invalid_value`; the row itself is imported and the raw value is kept as a notes line). The preview response also has `eventsEnriched` and `enrichedFields` (additive; see "Enrich existing events"). `NapperMeasurementsSummary` = `{totalRows, toCreate, alreadyImported, skipped, from|null, to|null (yyyy-MM-dd), skippedRows}`. Suggestion = `{token, occurrences, suggestion: "existing"|"create", medicationId|null, medicationName (catalog name, or the token for create), distance|null (0 = same ignoring case/diacritics), similarTokens: [other tokens of the file within typo distance], isMapped}`; listed only for medicine rows that will be created. `unmappedTokens` = names the import would reject with the given mappings (the preview applies mappings when sent, so preview and import of the same body report the same counts).
- `POST /babies/{id}/import/napper` (same body) -> 200 `{eventsCreated, eventsEnriched, enrichedFields: [{field, count}], measurementsCreated, createdMedications: [{id, name}], logs, measurements}` (summaries as in the preview; their `toCreate` is what was created). Every medication token of a new medicine row needs a mapping, else 422 `import_unmapped_medications` (ext `tokens`) and nothing is written. Mapping errors: `existing` id not in the baby's catalog, `create` without name, one token mapped twice differently -> 422 `import_invalid_medication_mapping` (ext `token`); create name > 100 chars -> 400. All inserts run in one transaction in chunks of 500 (medications, events, measurements); a concurrent insert of the same ids is 409 `import_conflict` and nothing is saved.
- Skip codes: `unknown_category`, `excluded_category`, `invalid_value`, `missing_value`, `duplicate_row`, `invalid_record` (domain rule, e.g. end before start, notes > 2000, a NUL character in a text or payload value, a payload value breaking the field rules such as a negative amount, measurement out of range or without values), `medications_ignored`. Invalid rows never abort the file.
- Idempotency: event id = UUID v5 (fixed namespace) of `baby|category|start UTC|end UTC|ordinal`, where `ordinal` numbers rows with the same category/start/end but different content; a row that would create exactly the same event as an earlier row is `duplicate_row`. Measurement id = UUID v5 of `baby|date|values (2 decimals)`; identical rows are duplicates. Medications created by an import get UUID v5 of `baby|normalized name`; a `create` reuses the catalog entry with that id (even after it was renamed, so re-importing never conflicts), else the entry whose normalized name equals the name. Ids that already exist (soft-deleted events included, so deleted imports are not resurrected) count as `alreadyImported`: re-importing creates nothing.
- Mapping (built-in types, `createdBy` = caller, Napper `comment` -> notes except for medicine; every mapped payload passes the same payload field rules as the API, else the row is `invalid_record`): BOTTLE -> feeding `{method:"bottle", amount_ml, bottle_feeding_type}` (`formula`|`breast_milk` from Napper's FORMULA|BREAST_MILK, case-insensitive; unknown content kept as a notes line), end = start when empty (an end Napper stored is kept: the bottle's duration). PUMPING, BREAST_PUMP -> breast_pump `{amount_left_ml, amount_right_ml}` (empty amounts left out), end = start when empty. NURSING -> feeding `{method:"breast", side: left|right|both from non-zero seconds, breast_left_seconds, breast_right_seconds, pause_count, paused_seconds}`; when Napper stored an instant, end = start + left + right seconds. CHANGED_DIAPER -> diaper `{content}` (WET|DIRTY|MIXED, case-insensitive; else `missing_value`), instant. NAP -> sleep `{kind:"nap"}` plus the sleep detail fields and pause keys below; NIGHT_WAKING -> sleep `{kind:"night_waking"}` plus pause keys, its sleep columns become notes lines ("Mood on wake-up: ..", "Mood on sleep: ..", "How baby slept: ..", "How baby woke: ..", "Time to fall asleep: ..") because detail fields do not apply to that kind (empty end = `missing_value` for both); BED_TIME/WOKE_UP -> sleep instants `{kind: bed_time|woke_up}` (sleep columns as notes lines, pause columns ignored). The deprecated `mood` is no longer written. MEDICINE -> medication instant `{medications:[{medicationId, name}]}`; the comment is split on ` e `, ` and `, `&`, `,`, `+`, `/`, line breaks; a row whose tokens are all `ignore` is skipped. Matching normalizes case, diacritics and spaces; typo tolerance: names up to 3 chars exact, up to 7 one edit, longer two (Levenshtein, computed with a length precheck and a bounded band over names bucketed by length; the preview stops when the request is cancelled or times out).

- Detail columns (Domain `NapperDetails`; values compared trimmed, case-insensitively, spaces/hyphens as underscores; empty cells and zero pauses add nothing; a value that cannot be used is a skipped field kept as a notes line "<label>: <raw>", never a skipped row):

  | Napper column | Rows | Field | Mapping |
  |---|---|---|---|
  | `numberOfPauses` | NAP, NIGHT_WAKING, NURSING | `pause_count` | 1-100 (0 = left out) |
  | `pausedMinutes` | NAP, NIGHT_WAKING, NURSING | `paused_seconds` | minutes x 60, rounded; at most 86400 and at most the event's length |
  | `howBabySlept` | NAP | `how_slept` | IN_BED in_bed, WORN_OR_HELD held, BOTTLE bottle, NURSING nursing, STROLLER stroller, CAR car, SWING swing, NEXT_TO_ME / CO_SLEEPING next_to_me, OTHER other; any other value = `other` plus a notes line "How baby slept: <raw>" (not a skipped field) |
  | `howBabyWoke` | NAP | `how_woke` | contains NATURAL (WOKE_UP_NATURALLY) naturally; else contains WOKE, WOKEN or WAKE woken; else skipped |
  | `babyMoodOnWakeUp` | NAP | `mood_on_wake` | GOOD good, NEUTRAL neutral, BAD bad; else skipped |
  | `babyMoodOnSleep` | NAP | (none) | always a notes line "Mood on sleep: <raw>" |
  | `timeToFallAsleep` | NAP | `time_to_fall_asleep_minutes` | a number up to 240 is minutes, a larger one is seconds (/60); rounded to whole minutes (midpoint away from zero); negative, unreadable or over 240 minutes skipped |

  Assumptions (there is no Napper documentation; docs/design/SYNTHESIS.md section 7 lists `IN_BED`, `WORN_OR_HELD`, `BOTTLE`, `WOKE_UP_NATURALLY`, `GOOD|NEUTRAL|BAD` as seen in the owner's export): the other `howBabySlept` and `howBabyWoke` values are guesses from Napper's UI labels (unknown ones degrade to `other` / a skipped field, never a lost row), and the unit of `timeToFallAsleep` is unverified: values up to 240 are read as minutes, larger ones as seconds (more than 4 hours to fall asleep is implausible). Revisit with a real export.
- Enrich existing events (`options.enrichExisting: true`, preview and import; Parent/Owner like any import): re-importing cannot change events created by an earlier import (ids are idempotent), so this option fills, for rows whose deterministic id already exists for this baby, only the detail fields `how_slept`, `fall_asleep`, `time_to_fall_asleep_minutes`, `how_woke`, `mood_on_wake`, `pause_count`, `paused_seconds` that the stored event has no value for (absent or `null`). It never overwrites a value (a parent's edit wins), never changes times, type, notes, other payload members (e.g. `bottle_feeding_type`) or the deleted state, skips soft-deleted events and events whose type changed, and adds a field only if the stored event still passes its type's payload rules with it (e.g. sleep details are skipped when the kind was changed to night_waking; `paused_seconds` when the event was shortened below it). Each enriched event gets `updatedAt` = `clientUpdatedAt` = server now (a server-side change, like a delete), so clients receive it in the delta pull; a client edit carrying an older client time then loses to it. Reported as `eventsEnriched` (events) and `enrichedFields: [{field, count}]` (in the field order above, only fields filled at least once) in the preview and the import response; `0`/`[]` without the option. Saved in the same transaction as the inserts; an event deleted or changed between plan and save aborts everything with 409 `import_conflict`. Idempotent: a second run enriches nothing.

## Roles and permissions
Owner > Parent > Caregiver > Viewer (`Domain/Babies/BabyRoleRules`: `CanManageMembers` = Owner, `CanWrite` = Owner|Parent, `CanLogEvents` = Owner|Parent|Caregiver, `CanChangeEvent` = `CanWrite`, or `CanLogEvents` and the event's `createdBy` is the caller; `Domain/Events/RunningEventControl` for the running-event exception). Policies (`Api/Authorization/BabyPolicies`): `BabyRead` (any member), `BabyLog` (Caregiver and up), `BabyWrite` (Parent and up), `BabyManageMembers` (Owner), `BabyNote` (Doctor), `BabyMeasure` (Owner, Parent, Doctor). The Doctor is outside the Owner > Parent > Caregiver > Viewer order: she satisfies only Viewer and Doctor (docs/design/16-doctor-access.md). A Caregiver (e.g. a grandparent) logs events and edits or deletes only the events they logged. The decision for every route is the table in `code/api/tests/Lotties.Api.Tests/Authorization/EndpointRoleMatrixTests.cs`, tried over HTTP for every role, a non-member and an anonymous caller; a mapped route missing from it fails the build's tests.

| Edit the baby, invites, change roles, remove members, access log (`GET /access-log`) | yes | no | no | no | no |
| Leave the baby | yes (not the last owner) | yes | yes | yes | yes |
| Shared catalog: search, add a community product (instance-wide, no baby) | yes | yes | yes | yes | yes |
| Own professional profile (`/me/professional-profile`, user level) | yes | yes | yes | yes | yes |

- Invites carry any role (Parent, Caregiver, Viewer, Owner or Doctor); accepting joins with it (a Doctor invite needs the accepting user's professional profile, else 422 `professional_profile_required`). The Owner changes a member's role among all five (to Doctor only with her profile; the web offers no role picker for a doctor, who is invited and removed); the last Owner can neither be demoted nor removed (409 `last_owner_required`). Deleting a baby and exporting do not exist.
- Running-event exception (owner decision 2026-10-22): a Caregiver's `PUT` of someone else's event is allowed only when the stored event is running (`endedAt` null, not deleted) and the body keeps `typeId`, `startedAt` and `notes` (compared as stored: UTC microseconds, trimmed, blank = none); `endedAt` stays null or is at or after the start and at most 5 minutes ahead of the server clock; only the pause keys (`pause_count`, `paused_seconds`, `paused_at`) change, and other payload members are only added where the stored value was absent, `null` or `""` (every other stored value stays, as a JSON value). A body identical to the stored event (an idempotent retry of an applied stop) is a no-op 200. Mirrored offline by `code/web/src/baby/permissions.ts` `isRunningControlChange`/`canControlTimer` (a nursing session stays locked: resuming moves its `side_since`).
- `event_not_owned` (403, problem+json with `code`): a Caregiver's `PUT` beyond that exception or `DELETE` of an event someone else logged, checked for every write to a stored event (also stale replays and already deleted or stopped events), after the other-baby check (409 `event_baby_mismatch`). A 403 for a role the policy rejects (e.g. demoted to Viewer) has no `code`.
- Sync (events are pushed one request per queued change, so every item is accepted or refused on its own): the web outbox drops a change refused with `event_not_owned`, puts the server copy back (an edit or delete of someone else's entry is reverted) and says so once; a 403 without a code (the role changed, e.g. while offline) dead-letters the change (out of the queue; Settings > Sync can retry or discard it), keeping the user's own entries on screen. Either way the rest of the queue syncs.

## Authorization behavior
Unauthenticated -> 401. Authenticated non-member (or unknown baby) -> 403 (does not reveal baby existence differently). Insufficient role -> 403. Users are provisioned on first authenticated request that needs them, keyed by the token's `iss` + `sub` (the same `sub` from another issuer is another user). Users created before migration `Wave2Hardening` have issuer `''` (a migration cannot read `Auth:Authority`); the first sign-in with their `sub` records the token's issuer on that row, after which it only matches that issuer.
