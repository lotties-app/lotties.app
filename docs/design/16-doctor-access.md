# Doctor access: professional profile, Doctor role, notes, consultation measurements, access log (step 1), suggestions the parents accept or decline (step 2) (design, 2026-10-22)

> Since 2026-10-22 the Owner chooses which sections each doctor sees (daily log, growth, medications, vaccines, formulas, notes; all six by default) and a doctor works in her own dashboard (`/doctor`) with on-demand, section-filtered reads instead of syncing her patients like a parent: docs/design/19-doctor-dashboard.md. Where this document says the Doctor reads "everything" (sections 2, 5, 7), read "the sections the family shares"; members are never hers.

Owner request: a pediatrician follows her patients in the app. She registers an account like anyone (Keycloak), declares herself a healthcare professional, and a baby's Owner invites her with the new role **Doctor**. One doctor account can follow many babies (her patients). Step 1 (sections 1-9) gives her read access, notes and consultation measurements, and gives the family an access log. Step 2 (section 10) lets her suggest prescriptions and recommendations that the parents accept or decline, with provenance on the accepted prescriptions, the parents' inbox and the `doctor_suggestion` push.

## 1. Professional profile (`professional_profiles`)
- One per user (`user_id` is the key and a foreign key to `users`): `kind` (`doctor`, the only kind in v1, stored as lower-case text), `display_name` (required, 1-100: the name families see), `specialty` (optional, 100), `registration_number` (optional, 40, e.g. a CRM), `verified` (boolean, default false), `created_at`, `updated_at`. Domain `Professionals/ProfessionalProfile.cs`, `ProfessionalProfileTerms.cs`.
- **Self-declared in v1.** Nothing sets `verified` (no API field, no admin tool yet), and every screen that shows a doctor's name shows "Self-declared doctor" ("Médico(a) autodeclarado(a)") next to it: notes, members, measurements, the access log, the profile form itself. The app never claims it checked a registration. Step 2 renders "Verified professional" when an operator set `verified` by SQL (section 10.6).
- `GET /me/professional-profile` (any signed-in user; 404 `professional_profile_not_found` before she declares one), `PUT /me/professional-profile {kind?, displayName, specialty?, registrationNumber?}` (201 declared / 200 updated; text trimmed, blank optional text is absent, NUL refused: 400 `validation_failed` with `field`). Any user may declare one; it does nothing by itself.
- Web: Settings > "I'm a healthcare professional" ("Sou profissional de saúde"): the form (name shown to families, specialty, registration number) with the self-declared notice. The name is typed without a title: screens add "Dr." (pt-BR "Dr(a).") and drop a title she typed anyway ("Dra. Ana" reads "Dr(a). Ana", never "Dr(a). Dra. Ana"; `notes/noteModel.ts` `doctorNameOf`).

## 2. The Doctor role
`BabyRole.Doctor`, stored by name in `baby_members.role` like the others (text, max 16, no check constraint: verified, so no schema change for the role itself). It sits outside the Owner > Parent > Caregiver > Viewer order (`Domain/Babies/BabyRoleRules`): `Satisfies(Viewer)` is true (she reads), `Satisfies(Doctor)` is true only for the Doctor, every other requirement is false.

| Action | Owner | Parent | Caregiver | Viewer | Doctor |
|---|---|---|---|---|---|
| Read baby, events (Day, Now), event types, medications, prescriptions and status, formulas, vaccinations, measurements, predictions (Insights), notes, catalog | yes | yes | yes | yes | yes |
| Read the members list and the appointments (every appointment route; section 11) | yes | yes | yes | yes | no (403) |
| Log, edit or delete events | yes | yes | own | no | no |
| Event types, medications, prescriptions, formulas, appointments (writes) | yes | yes | no | no | no |
| Measurements: add | yes | yes | no | no | yes (consultation measurements) |
| Measurements: edit or delete | any | any | no | no | her own only (403 `measurement_not_owned`) |
| Notes: write, edit and delete her own | no | no | no | no | yes (403 `note_not_owned` on someone else's) |
| Edit the baby, invites, roles, remove members, access log | Owner only | no | no | no | no |
| Napper import | yes | yes | no | no | no |
| Reminder preferences and baby reminders | yes | yes | yes | no | no |
| Leave the baby | yes (not the last owner) | yes | yes | yes | yes |
| Step 2: read prescription proposals | all | all | none (`[]`, 404) | none (`[]`, 404) | her own |
| Step 2: create, edit, withdraw a proposal | no | no | no | no | her own pending ones |
| Step 2: accept or decline a proposal | yes | yes | no | no | no |
| Step 2: mark a note read, list own reads | yes | yes | yes | yes | yes |
| Step 2: `doctor_suggestion` push | opt-in | opt-in | no | no | no |

- Policies (`Api/Authorization`): `BabyNote` (Doctor) for note writes; `BabyMeasure` (Owner, Parent or Doctor; a requirement may name alternative roles) for measurement writes; reads stay `BabyRead`, except the family's non-clinical records (appointments, members list), which need `BabyReadFamily` (any member but the Doctor, section 11). The decision of every route is in `EndpointRoleMatrixTests` (a Doctor column for every route; appointment routes and `GET /members`: refused, 403).
- **Reminders:** `NotificationRules.CanReceive` is `CanLogEvents`, so a Doctor is excluded everywhere the planner and the recipient loaders look (dose, nap, belly pain, fussy, overtired, diapers, appointments); `PUT /notification-preferences` is 403 for her and `GET /push/preferences` says `canReceive: false`.
- **Invites:** the Owner invites with role `Doctor` (any other role can be invited as before). Accepting a Doctor invite needs the accepting user's professional profile: 422 `professional_profile_required` otherwise, and the invite stays usable. The web accept screen shows the profile form inline ("Join as the baby's doctor"), saves it, accepts the same invite again and lands on Patients. Changing a member's role to Doctor needs her profile too (same 422); the web offers no role picker for a doctor row: doctor access starts with an invite and ends with a removal. A Doctor cannot invite (Owner only).
- **Removal:** the Owner removes a doctor at any time (Members). Her notes stay; they read "Dr. Ana Souza (no longer has access)" (the web compares the author with the members list; offline, and for a Doctor reader, who never gets the members list, the suffix is left out). Her consultation measurements stay, still "Recorded by Dr. ...".
- Strictly per baby: every read is the baby-scoped `BabyRead` policy of that one baby's membership. A doctor following Lia sees nothing of her siblings unless the family invites her there too.

## 3. Notes (`baby_notes`)
- `id` (client GUID), `baby_id`, `author_user_id`, `kind` (`note` | `recommendation`; step 2 gives recommendations their inbox and push), `visibility` (`shared` | `private`), `body` (1-4000, trimmed, line breaks kept), `created_at`, `updated_at` (server receive time, delta cursor), `client_updated_at` (client edit time, decides conflicts), `deleted_at` (soft delete). Domain `Notes/BabyNote.cs`, `NoteTerms.cs`.
- Sync contract as for formulas and appointments: `GET /babies/{id}/notes?since=` (any member; deleted included, by `(updatedAt, id)`), `GET /notes/{noteId}` (deleted included), `PUT /notes/{noteId} {kind?, visibility?, body, updatedAt?}` (the Doctor: 201/200; replay changes nothing; stale client time ignored; a deleted note stays deleted; another baby's id 409 `note_baby_mismatch`), `DELETE /notes/{noteId}` (soft, 204, idempotent).
- **Visibility is enforced on the server, in every read:** the list and the delta query filter `visibility = 'shared' OR author_user_id = reader` in SQL (`EfNoteRepository`), so a private note never leaves the database for anyone but its author; by id it is 404 `note_not_found`, the same answer as an unknown id; a write or delete by someone else on it is 404 (`PUT`) or a no-op (`DELETE`), never 403, so its existence is not revealed. Shared notes go to every member (Viewers and Caregivers too).
- **Only the author** edits or deletes a note (403 `note_not_owned` on a shared note of someone else). Owners and Parents read shared notes and cannot edit or hide them in v1.
- **A shared note never becomes private again** (422 `note_already_shared`): the other members already have it on their devices, and a private note is never sent to them, so they could not learn the change. Private to shared is allowed (they receive it as new). The author deletes a shared note to take it back; the delete reaches everyone through the delta.
- Each response carries `author: {userId, displayName, professional}` (the professional name when she declared one), resolved at read time.
- Web: Dexie schema v6 table `notes` (`id, babyId, [babyId+updatedAt]`), pulled after appointments (`notes/noteSync.ts`, cursor `notes`; a deletion always wins), pushed through the outbox (`entityType: 'note'`; a delete absorbs a queued edit), purged with the baby. Route `/notes` (Settings entry "Notes", and each Patients card): the timeline newest first, each note with the author's name and the self-declared badge, date, kind chip and visibility chip ("Shared with parents" / "Private"), edit and delete for the author; the composer sheet (kind chips, "Who sees it": Shared with parents (default) / Only me, disabled with a hint for a shared note, the text). Parents read with a notice; nobody but the author sees buttons.

## 4. Consultation measurements
- The existing measurements entity and routes: a Doctor may `PUT` a new measurement and edit or delete only her own (`Measurement.EnsureChangeableBy`, 403 `measurement_not_owned`); Owners and Parents add, edit and delete any, as before.
- Additive column `measurements.recorded_by_doctor` (boolean, default false; the creator's role was Doctor), and additive response fields `recordedByDoctor` and `recordedBy` (`PersonSummary`, only when recorded by a doctor).
- Web (Insights > Growth and its list): the doctor gets "Add measurement" and edit/delete on her own rows; every measurement a doctor recorded reads "Recorded by Dr. Ana Souza (self-declared doctor)".

## 5. Patients (the doctor's home)
- Route `/patients`: the babies where the user's role is Doctor, by name, each with age, the latest entry ("Last entry 2 hours ago"), and the number of shared notes she wrote, plus a Notes button. Tapping a card selects the baby into the usual views (Now, Day, Insights, Growth, Medications, Vaccines; never Appointments, section 11), which are read-only for her: the bottom bar keeps its tabs, the "+" is hidden (the Viewer mechanism: `canLog` is false), Now shows the view-only notice.
- Landing: a user whose babies are all Doctor memberships lands on `/patients` until she opens a patient in this browser session (a `sessionStorage` flag); everyone else with a Doctor membership finds "Patients" in Settings. Patients' data syncs like any baby's.

## 6. Access log (`access_log`)
- `id`, `baby_id`, `user_id`, `role` (by name), `kind` (`view`), `at`. Written by the server (an endpoint filter on the baby-scoped route group) when a Doctor is authorized for any `GET` of the baby's data, **at most once per hour per (doctor, baby)**: a new entry only when her latest is at least an hour old; the id is derived from the previous entry (step 2, section 10.8; step 1 used the UTC hour), so racing requests write one row. The doctor's app syncs all her patients, so an entry means "her device loaded the baby's data", background sync included.
- `GET /babies/{id}/access-log` (Owner): the newest 50, newest first, `[{userId, person, role, kind, at}]`. Web: Settings > Members & invites > "Access log" (who, role, when), read-only, online only.

## 7. Privacy (LGPD-aware)
- Health data of a child (LGPD art. 11, sensitive data; art. 14, children's data in the child's best interest, with a parent's specific consent). The legal basis for sharing with the doctor is the parent's explicit, specific consent at invite time: the Doctor invite shows "The doctor who accepts will see everything logged for Lia and can add notes and measurements. You can remove access at any time." ("O(a) médico(a) que aceitar vai ver tudo o que for registrado de Lia e poderá adicionar notas e medidas. Você pode remover o acesso a qualquer momento."). The brief's wording names the doctor ("Dr. X will see ..."); the doctor is not known when the invite link is created, so the line names her role.
- Purpose limitation and minimisation: access is per baby membership, never per family; the doctor gets no reminders and no write access to the family's log; private notes stay with their author.
- Transparency and revocation: the access log shows the Owner when each doctor loaded the data; removal is immediate (the next request is 403) and her device purges the baby on its next sync.
- Not done in v1 (recorded for the owner): verifying registrations (CRM lookup), a data processing notice inside the app, export or deletion requests of a doctor's notes after she is removed, and access log retention (rows are kept; 50 are shown).

## 8. Migration
`DoctorAccess` (after `Appointments`): creates `professional_profiles`, `baby_notes` (index `(baby_id, updated_at)`, `author_user_id`), `access_log` (indexes `(baby_id, at)`, `(baby_id, user_id, at)`), and adds `measurements.recorded_by_doctor` (NOT NULL DEFAULT false). Foreign keys to `babies` and `users` are `RESTRICT` like the other per-baby tables. Applied like every migration (docs/DEPLOY.md "Applying migrations").

## 10. Step 2: suggestions the parents accept or decline (design, 2026-10-22)
Owner request (decided): the doctor can **suggest** prescriptions and recommendations; the parents **accept or decline**. Nothing silently changes the baby's medicines: a suggestion is never active, never reminds and never enters the status calculator before an Owner or Parent accepts it, and the doctor never writes the baby's data directly (prescriptions, medications, events stay Owner/Parent writes; 403 for her).

### 10.1 Prescription proposals (`prescription_proposals`)
- Columns: `id` (client GUID), `baby_id`, `author_user_id` (the doctor), the medication reference `medication_id` (optional: a medication of the baby's list), `product_id` (optional: a shared catalog product, checked like a medication link: exists, not merged) and `medication_name` (required, 1-100: what the family reads; the picked medication's or product's name, or free text), the prescription payload with the **same Domain types and validation as prescriptions** (`DoseRule` with per-kg and rounding and the counted-unit rules, `PrescriptionSchedule`: scheduled by `timesOfDay`, `everyMinutes` or `dayParts` (+ optional `dayPartReminders`) or as needed with `minIntervalMinutes`/`maxDosesPer24h`/`indication`; `interval_group`; `start_date`/`end_date` with the prescription date rules; `instructions` up to 2000), `replaces_prescription_id` (optional: the prescription this proposes to change), `status` (`pending` | `accepted` | `declined` | `cancelled` | `superseded`), `decline_reason` (optional, up to 500, the parent's words), `cancel_reason` (`withdrawn` | `access_removed`), `decided_by`, `decided_at`, `accepted_prescription_id`, `created_at`, `updated_at` (server receive time, delta cursor), `client_updated_at` (the doctor's edit time, decides conflicts), `xmin` row version. Domain `Proposals/` (`PrescriptionProposal`, `ProposalTerms` = `MedicationReference` + the prescription components, `ProposalStatus`, `PrescriptionSnapshot`).
- `instructions` of prescriptions widens from 1000 to 2000 characters (column and both validators) so an accepted proposal carries the doctor's text verbatim.
- **Lifecycle:** created `pending` by a Doctor. While pending, only its author edits it (`PUT`, last write wins on the client time) or withdraws it (`DELETE` = `cancelled`, reason `withdrawn`; the row stays). Once decided (`accepted`, `declined`, `cancelled`, `superseded`) it is **immutable**: an edit is 409 `proposal_decided` (an unchanged replay returns the stored copy), a withdraw is a no-op. A change of an accepted prescription is a **new** proposal with `replacesPrescriptionId`.
- **Accept** (Owner or Parent, `POST .../accept {prescriptionId, acceptedOn?}`; the client generates the new prescription id so a queued offline accept applies once) is **one transaction**: the medication is resolved (the referenced medication of the baby; else the baby's medication linked to the product; else one with the same name; else a new one, id derived from the proposal, linked to the product), the prescription is created from the payload (`status active`, `prescriber` = the doctor's name) with provenance (10.2), the proposal becomes `accepted` (`decided_by`, `decided_at`, `accepted_prescription_id`); when it replaces a prescription that is still there, that one is **ended** by the existing lifecycle (status `stopped`, `end_date` = the accept day `acceptedOn` (client local date, default the UTC date), kept within its course; never deleted, `changed_by_parent` untouched) and other pending proposals that replace the same prescription become `superseded`. A replay (already accepted) returns the stored outcome; accepting a declined, cancelled or superseded proposal is 409 `proposal_not_pending`; a lost race is 409 `concurrent_modification` (retry reads the winner).
- **Decline** (Owner or Parent, `POST .../decline {reason?}`): `declined` with the optional reason, which the doctor sees. Replay returns the stored copy; declining an accepted, cancelled or superseded proposal is 409 `proposal_not_pending`.
- **Access removed:** removing a doctor (or her leaving, or a role change away from Doctor) cancels her pending proposals in the same save (`cancelled`, reason `access_removed`). Her decided proposals stay.
- **Visibility (server side, every read):** the author doctor sees her own proposals and their statuses; Owners and Parents see every proposal of the baby; Caregivers, Viewers and other doctors see none: the list and the delta are empty for them and `GET` by id is 404 `proposal_not_found` (the same answer as an unknown id). The filter is in the SQL query (`EfPrescriptionProposalRepository`).
- Routes (under `/babies/{id}`): `GET /prescription-proposals?since=` (filtered list/delta by `(updatedAt, id)`), `GET /prescription-proposals/{proposalId}` (404 when not visible), `PUT /prescription-proposals/{proposalId}` (Doctor: 201 created / 200; another baby's id 409 `proposal_baby_mismatch`; another doctor's 404; `medicationId` not of the baby 422 `prescription_medication_not_found`; `replacesPrescriptionId` not a live prescription of the baby 422 `replaced_prescription_not_found`), `DELETE /prescription-proposals/{proposalId}` (Doctor: withdraw own pending, 204, idempotent; unknown, decided or someone else's is a no-op), `POST /prescription-proposals/{proposalId}/accept` and `/decline` (Owner, Parent: 200 `{proposal, prescription}`; `prescription` is the created one on accept, `null` on decline). Each proposal carries `author` (`PersonSummary`, resolved at read time).

### 10.2 Provenance on prescriptions
- Additive columns on `prescriptions`: `prescribed_by_user_id`, `prescribed_by_name` (snapshot of the doctor's display name at accept time, stored without a title: screens add "Dr."/"Dr(a)." as for notes), `proposal_id`, `original_snapshot` (jsonb: the proposal payload as the doctor sent it), `changed_by_parent` (NOT NULL DEFAULT false). All nullable or defaulted: existing rows stay valid and read as parent-entered.
- A parent's edit of a doctor-sourced prescription is allowed and sets `changed_by_parent = true` when the content (anything but the active/stopped status) changes; it is never reset and `original_snapshot` is kept. Stopping or resuming is not a change; ending by a replacement is not a change.
- Response fields: `prescribedByUserId`, `prescribedByName`, `prescribedBy` (`PersonSummary` at read time, for the verified/self-declared badge), `proposalId`, `changedByParent`, `original` (`{medicationName, productId, kind, dose, timesOfDay, everyMinutes, dayParts, dayPartReminders, minIntervalMinutes, maxDosesPer24h, indication, intervalGroup, startDate, endDate, instructions}`). Every member reads them (Caregivers, Viewers and the Doctor read-only).
- Web: the Meds tray card and the prescription details read "Prescribed by Dr. Ana Souza" with the self-declared or verified badge; when changed, "Changed by parent" and "See what Dr. Ana prescribed" opening the original read-only.

### 10.3 Recommendations inbox (`note_reads`)
- `note_reads` (`note_id`, `user_id` key; `baby_id`; `read_at` server time): one row per member and note, the first read kept. `PUT /babies/{id}/notes/{noteId}/read` (any member who sees the note; 200 `{noteId, readAt}`; 404 `note_not_found` otherwise), `GET /babies/{id}/note-reads?since=` (the caller's own reads, by `readAt`).
- Unread = a shared note of kind `recommendation`, not deleted, not written by the reader, without her read. Opening it marks it read (offline through the outbox).
- Web for Owners and Parents: an inbox card on Now per pending proposal ("Dr. Ana suggested a prescription": details sheet with the dose and schedule summary, the doctor's instructions, Accept / Decline with an optional reason and "Accepting adds this prescription to Lia. You can end it at any time.") and per unread recommendation ("Dr. Ana sent a recommendation": opens the note and marks it read); the "From your doctor" page (route `/from-doctor`) lists pending proposals, decided proposals and recommendations; an unread badge on its Settings entry.

### 10.4 Push: `doctor_suggestion`
- One kind for new proposals and new shared recommendations. Recipients: Owners and Parents with the per-baby switch "Doctor suggestions" (`baby_notification_preferences.doctor_suggestions`, default off; a Caregiver may store it but never receives) and the device opt-in. The doctor, Caregivers and Viewers are never recipients; the author is never a recipient.
- Planned per suggestion while it is new (created less than 24 hours ago), still pending (a proposal) or not deleted and not read by the recipient (a recommendation). Sent from the creation time; inside quiet hours it waits for their end (quiet hours always apply); expires 24 hours after the creation. Keys `proposal:{id}` and `recommendation:{id}` (one per suggestion and member). Urgency normal, no snooze.
- Payload codes and ids only: `{kind: "doctor_suggestion", babyId, proposalId | noteId, at}` (+ `names.baby` with show-names on). Lock screen: "Your doctor sent a suggestion" ("Seu médico enviou uma sugestão"); never a medicine name, dose or note text. A click opens "From your doctor".
- The doctor gets no push in v1: her proposal list shows the decision on the next sync.

### 10.5 Doctor UI
- Patient view: "Prescribe" opens the prescription sheet in proposal mode (the same editor: medication picker with the baby's list, the catalog and ingredient search without adding anything to the baby's list, dose with unit and per-kg rules, every schedule type including part of the day, course dates, instructions; no prescriber field; "Send to parents"). "My proposals" lists hers per patient with status chips (Pending, Accepted, Declined with the reason, Cancelled, Replaced), edit and withdraw for pending ones, "Propose a change" on an accepted doctor-prescribed prescription (prefilled, sets `replacesPrescriptionId`). Offline: create, edit and withdraw queue in the outbox.
- Recommendations: the existing composer (kind `recommendation`, shared) feeds the inbox and the push.

### 10.6 Verified flag
- The badge reads "Verified professional" ("Profissional verificado") when `verified` is true and "Self-declared doctor" otherwise. Nothing in the app sets it (no admin tooling in v1). A future operator step, by SQL on the database (after checking the registration out of band): `UPDATE professional_profiles SET verified = true, updated_at = now() WHERE user_id = '<user id>';` (and `false` to revoke).

### 10.7 Guardrails
- The app carries what the doctor wrote and does not judge it; proposals use the prescription validation (impossible values rejected, per-kg and counted-unit rules); the early-dose confirmation is unchanged; no copy implies the app recommends a dose; "Self-declared" stays next to her name unless verified.
- LGPD: access stays per baby and revocable; removing the doctor cancels her pending proposals; the access log keeps recording her reads, at most one entry per hour per doctor and baby, also under a burst of parallel requests across an hour boundary (10.8).

### 10.8 Access log throttle fix
Step 1 checked the latest entry and derived the id from the UTC hour: two parallel requests of one sync burst on both sides of an hour boundary (10:59:59 and 11:00:00) both saw an old entry and wrote two rows a second apart. The id of a new entry is now derived from the previous entry's id (or "first"), so every request that read the same latest entry writes the same id and only one insert wins; the hourly check is unchanged.

### 10.9 Data model and migration `DoctorProposals` (after `DoctorAccess`)
- `prescription_proposals` (flattened like `prescriptions`, the same dose and schedule columns; foreign keys to `babies` and `users` RESTRICT; indexes `(baby_id, updated_at)`, `(baby_id, author_user_id)`, `(baby_id, status, created_at)`; `xmin` row version), `note_reads` (key `(note_id, user_id)`, cascade from the note, index `(baby_id, user_id, read_at)`), the provenance columns of `prescriptions` (nullable; `changed_by_parent` NOT NULL DEFAULT false), `prescriptions.instructions` widened to 2000, `baby_notification_preferences.doctor_suggestions` NOT NULL DEFAULT false and the candidate index filter widened to it (dropped and created again). No row is updated or deleted; existing rows stay valid. Applied like every migration (docs/DEPLOY.md "Applying migrations").
- Domain `Proposals/` (`PrescriptionProposal`, `ProposalTerms`, `MedicationReference`, `ProposalVisibility`, `ProposalMedications`, `ProposalAcceptance`), `Prescriptions/PrescriptionSnapshot.cs`, `Notes/NoteRead.cs`; Application `Proposals/` (`PrescriptionProposalService`), `NoteService` (reads), `MemberService` (cancel on removal); Api `ProposalEndpoints`, policy `BabyPropose`.

## 11. Doctor read audit (2026-10-22)
Owner finding after trying doctor access: a Doctor could read the baby's **appointments**, which may name other doctors, clinics and private reasons. Fixed, together with the one other unambiguous leak found (the members list); everything else a Doctor reads is listed below for the owner to decide.

### 11.1 What changed
- **Server.** New policy `BabyReadFamily` (`BabyFamilyRequirement` + `BabyFamilyHandler`, rule `BabyRoleRules.CanReadFamilyRecords`: Owner, Parent, Caregiver, Viewer; never the Doctor). Every appointment route sits in a route group that requires it (`AppointmentEndpoints`: list with its `since` delta and `from`/`to` range, by id, the `PUT`; a route added to the group later inherits it), and `GET /members` requires it. A Doctor gets **403** (the policy's answer, like every other role refusal; a 404 would only hide existence, and the routes are not per-item secrets), a refused read writes no access log entry, and she can still leave (`DELETE /members/me` stays `BabyRead`). No aggregate endpoint carries appointments (predictions, babies, push preferences, vaccinations checked), and the planner never sends her an `appointment_reminder` (`NotificationRules.CanReceive`; test added).
- **Web.** `canSeeAppointments` / `canSeeFamilyRecords` (`baby/permissions.ts`): for a Doctor there is no "Next appointment" card on Now, no appointments strip and no calendar button on Day, no Settings > Appointments entry, and `/appointments` redirects to `/patients` before the calendar renders. The sync never pulls appointments for a Doctor membership and drops the local copies and their cursor on every pull (`syncAppointments`/`dropAppointments` in `sync/pull.ts`), so copies kept from an earlier family role are purged as soon as the role is Doctor; a change back to a family role pulls them all again. `useMembers` and Settings > Members never ask for the members list for a Doctor (she keeps "Leave this baby"); without the list, Day shows no "logged by" names and Notes no "(no longer has access)" suffix for her, as offline.
- The Doctor invite's consent line ("will see everything logged for Lia") is unchanged: appointments are planned visits, not logged data.
