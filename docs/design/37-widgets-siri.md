follows the same data contract later. **Status (2026-10-31): written, not yet compiled or run.** There is no Xcode on the
development machine; the workflow `.github/workflows/ios-compile-check.yml` (unsigned build on a macOS runner) is the

## 1. Decisions (owner, 2026-10-31)

| Question | Decision |
| --- | --- |
| What does a Siri phrase, widget button or quick action do? | **Logs the event at once**, offline, and syncs later. No confirmation sheet. |
| First cut | **iOS only** (WidgetKit + App Intents). Android widget and shortcuts later, same contracts. |
| Where do the intents run | In the **app target** (App Intents work without an extension since iOS 16), so there is one extension only: the widget. |

Minimum iOS for the new code: 16 (the Xcode project says 15 today; the App Intents and widget code is guarded with
`@available(iOS 16, *)` or the target version is raised, an owner decision at step 2).

## 2. Data flow (the app is offline-first; neither widget nor intent talks to the network)

```
web app (WebView, Dexie)  --writeSnapshot-->  App Group container  <--reads--  widget (WidgetKit)
                                                      ^   |
Siri / widget button (App Intent) --append--> outbox  |   +-- app drains the outbox on launch and resume,
                                                          turns each entry into a normal local event (same write path
                                                          as the UI), then removes it
```

App Group: `group.app.lotties.app`, shared by the app and the widget extension. Both files live in its container, not in
the WebView's storage (a native process cannot read IndexedDB).

### 2.1 `widget-snapshot.json` (written by the app)

```json
{
  "version": 1,
  "updatedAt": "2026-10-31T21:05:00Z",
  "signedIn": true,
  "selectedBabyId": "<guid>",
  "babies": [
    {
      "id": "<guid>",
      "name": "Ana",
      "sleep": { "state": "asleep", "startedAt": "2026-10-31T20:40:00Z" },
      "lastFeed": { "at": "2026-10-31T19:10:00Z", "kind": "bottle", "amountMl": 120 },
      "lastDiaper": { "at": "2026-10-31T20:05:00Z", "kind": "wet" }
    }
  ]
}
```

Times are absolute; the widget renders "x min ago" itself, so it stays right without the app. `signedIn: false` (or a
missing file) makes the widget show "Open Lotties". The app rewrites the file after every local event write and after
each sync pull (one writer function, only when `isNativeApp()`), and **deletes it on sign-out** and when the account's
local data is cleared (docs/design/12 "per-account local data").

### 2.2 `widget-outbox.json` (appended by intents, drained by the app)

```json
[
  { "id": "<client guid>", "babyId": "<guid>", "type": "feed", "occurredAt": "2026-10-31T21:07:12Z",
    "payload": { "kind": "bottle", "amountMl": null }, "source": "siri" }
]
```

The `id` is the event GUID the client generates (project convention), so draining is an idempotent upsert: a crash after
the write and before removing the entry just writes the same event again. `type` and `payload` use the app's own event
types and payload shapes (code/web, per-kind payload), never new ones; the exact mapping is step 3. File access from the
widget and the intent goes through `NSFileCoordinator` (two processes can touch it).

## 4. Signing impact (this changes the manual signing of docs/MOBILE-RELEASE.md 4.3)

The widget is a second bundle with its own App ID and profile, and both bundles need the App Group capability.

1. **Owner, developer portal** (needs no Mac):
   - Identifiers > **App Groups** > **+**: `group.app.lotties.app`.
   - Identifiers > `app.lotties.app` > enable **App Groups** and select that group > Save.
   - Identifiers > **+** > App IDs > App: `app.lotties.app.widgets`, enable **App Groups** with the same group.
   - Profiles: **regenerate** the existing `Lotties App Store` profile (a capability changed, the old one no longer
     matches) and create `Lotties Widgets App Store` (App Store Connect distribution, the new App ID, the same
     distribution certificate).
   - Secrets: replace `IOS_PROFILE_BASE64`, add `IOS_WIDGET_PROFILE_BASE64` (same commands as 4.3 step 5).
2. **Workflow** (assistant): install both profiles; export with a `provisioningProfiles` map with both bundle IDs.
   **The archive stops passing `PROVISIONING_PROFILE_SPECIFIER` on the command line** (one value would apply to both
   targets): each target carries its own profile name in the Xcode project (Manual style, distribution identity).
3. The App Store Connect API key is unchanged (upload only).

**Risk (step 2, taken: the project was edited by script and is checked by the compile workflow).** `App.xcodeproj` is a hand-readable `objectVersion 60` project without synchronized folders: every new
Swift file, the widget target and the entitlements need explicit edits in `project.pbxproj`. Writing them without Xcode,
only validated by a CI archive (about 6 minutes and $0.40 per try), works but can take several tries, and a bad edit
breaks the iOS build that works today. Safer: do step 2 once in Xcode on the MacBook (add the target, the files and the
capabilities in the UI, commit the resulting project), then the assistant continues from there. Pick one before step 2.

## 6. Privacy and safety

- The snapshot and the outbox hold a child's data on the device only, in the app's own App Group container; they are
  deleted on sign-out and account erasure, and never uploaded by themselves.
- Lock-screen variants hide names by default.
- Intents need no network and no token: they only append to the outbox; the app, signed in as the account, does the write.
- If the outbox holds entries for an account other than the signed-in one (a sign-out and another sign-in in between),
  they are dropped, not applied: entries carry no account id, so the outbox is cleared on sign-out.

## 8. Siri through the MCP server (decided 2026-10-31, after the widget shipped)

The owner asked for Siri to mirror the Alexa intents, answered by the same server. So the Siri and Shortcuts intents are
**MCP clients** (supersedes the "log at once, offline" decision of section 1 for Siri; the **widget buttons keep it**):

- `App/LottiesSiriIntents.swift`: 40 App Intents (the Alexa model's reads and logs that the MCP server has a tool for;
  medication has none by design), each one `tools/call` of the matching tool, speaking the answer. Ten of them have spoken
  phrases (`App/LottiesShortcuts.swift`, the iOS limit); all are in Shortcuts and Spotlight. Phrases and titles are localized: `App/en.lproj` and `App/pt-BR.lproj` `AppShortcuts.strings` (key = the English phrase with `${applicationName}`) and `pt-BR.lproj/Localizable.strings` (intent titles, descriptions, parameters). Pt-BR phrases name the app as "no Lotties" ("Registrar fralda no Lotties").
- `App/LottiesMcp.swift`: the sign-in (`ASWebAuthenticationSession`, PKCE, public client `lotties-ios`, scopes
  `lotties.read lotties.write offline_access`, redirect `app.lotties.app://siri/callback`), tokens in the Keychain (never in the
  App Group files the widget reads), refresh, and the JSON-RPC call (`Authorization: Bearer`, protocol 2025-11-25, one POST,
  no initialize). Keycloak setup: docs/MCP.md 3.4.
- Spoken sentence: the server renders it with the Alexa language classes when the request has the header
  `Lotties-Speech-Locale: pt-BR|en-US` (`structuredContent.speech`), so Siri says what Alexa says, in the phone's language.
- The web app starts the sign-in: Settings > Voice assistants > Siri and Shortcuts (`SiriConnectPanel`), through the WebKit
  message handler `lotties` (`siriStatus`, `siriConnect`, `siriDisconnect`; also used by the widget bridge). Logout and
  account erasure call `clearAll`, which also drops the Siri tokens.
- Offline: a Siri request needs the network (it says nothing was logged). No outbox fallback, to avoid double events when
  an answer is lost; idempotency keys make a retry safe. The widget buttons still work offline.
- The old offline intents (`LogDiaperIntent`, ...) stay for the widget buttons and are hidden from Shortcuts
  (`isDiscoverable = false`).

## 9. Next-up estimates and the "coming up" highlight (2026-11-01)

The snapshot carries the Now screen's estimates per baby: `nextNap {earliest, expected, latest}`, `nextFeed {at, amountMl?}`,
`nextDiaper {at, kind}`, built by `widgets/snapshot.ts` from the last predictions the app fetched (localStorage cache),
the cached age norms and the local events (`deriveNowState` and `upcomingToday`, the same code as the Now screen); no
network. Estimates only, never advice.

- Shown as "Próxima soneca 14:20", "próx. 15:10" (only while still ahead).
- **Coming up** (`WidgetSnapshot.Baby.due(at:)`): from 20 minutes before an estimate until 30 minutes after it (owner choice).
  That action's tile gets the category colour on its border and a tinted fill (the icon stays: a bell hid which action
  it was, owner feedback 2026-11-01); the sleep button turns into a filled "Soneca 14:20" while the nap estimate is coming up and the baby
  is awake. The wording stays a time, not an order ("estimates, not alarms").
- The widget timeline has an entry at each moment a highlight starts or stops (`dueChanges`), so it changes without the app
  opening; views read the entry's date from the environment (`lottiesNow`), never `Date()`.
- Logging from a widget button or Siri clears the matching estimate at once; the app republishes real ones when it opens.
- Staleness: the estimates are as old as the last time the Now screen fetched predictions online.

## 10. Choosing the buttons, and the Activities widget (2026-11-01)

- The Summary and Quick-actions widgets are configurable (iOS 17, `AppIntentConfiguration`, `LottiesButtonsIntent`):
  "Edit widget" picks what each of three buttons logs, from `WidgetActivity` (bottle, breast, diaper, bath, belly massage,
  tummy time, nasal suction, nail trim, skin care, outdoor, fussy). The sleep button stays. The widget extension's
  deployment target is 17.0 (the app stays 16.0; widget buttons already needed 17).
- The fixed **Activities** widget (medium) has a button for each of the eight non-everyday activities.
- One intent logs them all (`LogActivityIntent`, hidden from Shortcuts). Bottle and diaper keep their behaviour. The other
  activities go to the outbox as `type: "activity"` with `payload.kind` = the event type key; the app creates an instant
  event, or a running one when the type has a duration (stop it in the app), through `createEvent`. A key outside
  `widgets/activities.ts` or a type the baby lacks is dropped.
- The snapshot carries `lastActivity` (type key to last start, 3 days back) so rows can say "há 3 h".
- Picker names in "Edit widget" follow the phone language (English literals; the tiles follow the app language).
