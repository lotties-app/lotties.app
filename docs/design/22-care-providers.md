# Care providers: "My doctors", a per-baby directory picked from the appointment form (design, 2026-10-23)

Owner request: keep the baby's doctors and clinics once, with phone, address and professional registration, and when scheduling an appointment pick one so the details fill in on their own instead of being retyped. The app keeps what the family entered; it never suggests a provider or checks a registration.

## 1. Decisions (owner defaults)
- Per baby, shared by every member who may see appointments (Owner, Parent, Caregiver, Viewer). Owners and Parents create, edit, favorite and delete; Caregivers and Viewers read and use the links. **The Doctor role never sees or edits the directory**: the entries are the family's own doctors and clinics (docs/design/16-doctor-access.md section 11), so every route is 403 for her, the web never asks and purges local copies.
- Soft delete (`isDeleted`), idempotent upsert with a client GUID, delta sync with the server `updatedAt` as cursor and the client `updatedAt` deciding conflicts: the formulas and appointments contract.
- The appointment keeps its own free-text `location` and `doctorName`. Picking a provider **copies** text into them and stores `providerId` as a plain link. Editing the appointment afterwards never rewrites the provider; deleting or editing a provider never rewrites an appointment (the copied text stays).
- Contact details only. The notes field says so ("the baby's health information goes in the baby's own records"); the server cannot check it, so it is a prompt, not a rule.

## 2. Data model (Domain `CareProviders/`, table `care_providers`, migration `CareProviders`)
`CareProvider`: `id` (client GUID), `babyId`, `name` (required, 1-80), `specialty` (free text, 60), `registrationCouncil` (20), `registrationNumber` (30), `registrationRegion` (10) (three free texts, e.g. CRM / 123456 / SP; no format is enforced), `clinicName` (120), `address` (400, one multi-line text), `phone` (30), `whatsapp` (30), `email` (120), `website` (200), `notes` (1000), `isFavorite`, `isDeleted`, `createdBy`, `createdAt`, `updatedAt` (server receive time, the delta cursor), `clientUpdatedAt`. Text is trimmed, blank optional text is absent, NUL is rejected (400 `validation_failed`, `field`). A `website` that names a scheme must name `http` or `https` (`javascript:`, `data:` and the like are 400, `field: website`); one without a scheme (`clinic.example/ana`, `localhost:8080`) is kept and the web adds `https://` when it makes the link.
- Indexes: `(baby_id, updated_at)` for the delta. FK to the baby and the creator, restrict. No query filter: deleted rows must reach other devices through the delta.
- `appointments.provider_id` (uuid, nullable) in the same migration: **no foreign key**. An offline client may push an appointment before its provider (or the provider was deleted), and a link to a missing provider is harmless: the web resolves it locally and falls back to the copied text. The id is not validated against the baby either; the web only ever looks it up in the baby's own directory.

## 3. API (`/api/v1/babies/{babyId}/care-providers`)
- `GET ?since=` (Owner, Parent, Caregiver, Viewer; policy `ReadFamily`): the baby's providers, deleted ones included, ordered by `(updatedAt, id)`; `since` = `updatedAt >= since`. No paging.
- `PUT /{providerId}` (Owner, Parent; `Write`): the full state `{name, specialty?, registrationCouncil?, registrationNumber?, registrationRegion?, clinicName?, address?, phone?, whatsapp?, email?, website?, notes?, isFavorite?, isDeleted?, updatedAt?}`; 201 + `Location` / 200; an unchanged replay changes nothing (not even `updatedAt`), a stale client time is ignored (200, stored copy), an id of another baby is 409 `care_provider_baby_mismatch`. No `GET` by id and no `DELETE` (405): `isDeleted` is the soft delete and restoring is the same route.
- `PUT /appointments/{id}` gains `providerId?` (and `AppointmentDto.providerId`); absent or `null` = no link.
- Role matrix rows in `EndpointRoleMatrixTests` (`ReadFamily` for the GET, `Write` for the PUT) and `CareProviderEndpointTests` (every route x Doctor = 403 with no provider in the body).

## 4. Web
- Dexie schema v9 `careProviders` (`id, babyId, [babyId+updatedAt]`), cursor `careProviders`, outbox `entityType: 'careProvider'` (no dependency: the appointment's `providerId` is only a link), pulled after the appointments for the family roles (`sync/careProviderSync.ts`: `syncCareProviders` never asks for a Doctor and drops her copies and cursor, as `syncAppointments`), purged with the baby. Commands in `db/careProviderCommands.ts` mirror the API rules (name 1-80, limits, a website with another scheme is dropped instead of sent) and queue the full state; a later edit absorbs a queued one.
- Hub entry **Doctors and clinics** (`providers`, Baby care, after Appointments; hidden from the Doctor), route `/hub/providers` (`HubProvidersPage`; a Doctor is sent to her patients). `ProvidersScreen`: search (name, translated specialty, clinic, registration, address; accents ignored), favorites first then by name, rows with specialty, clinic and registration, a favorite star with a name for screen readers, an empty state that explains the benefit ("Save the pediatrician, specialists and clinics once ... pick one and the doctor and place fill in on their own"), "Add doctor or clinic" for writers and the read-only line for the others.
- `ProviderDetailSheet`: registration, clinic, the contact links (`ProviderContact`: call `tel:`, WhatsApp `https://wa.me/<digits>` (needs the country code, said in the form), e-mail `mailto:`, website, the address text and "Open in maps" = a Google Maps search of the address on one line, else the clinic name; external links open in a new tab with `noopener noreferrer`), notes; Owners and Parents also Edit, mark/unmark favorite and Delete with Undo.
- `ProviderSheet` (add / edit): name, specialty as free text with chips for the suggested ones (pediatrician, dermatologist, ENT, cardiologist, allergist, gastro, ophthalmologist, orthopedist, dentist, other), council + state, registration number, clinic, address (multi-line), phone, WhatsApp, e-mail, website, notes, "Favorite". A suggested specialty is **stored by its code** (`pediatrician`) so each device shows it in its own language; any other text is stored and shown as typed. The sheet stops its submit event: it opens inside the appointment form's React tree (a portal) and the submit would otherwise save the appointment too.
- Appointment form: `ProviderPicker` above Place and Doctor: search the saved ones (five shown, favorites first), tap one to fill `doctorName` (the provider's name) and `location` (clinic, then the address on one line, within 200 characters) and set `providerId`; "Add new provider" opens `ProviderSheet` inline and selects the new one; once picked the provider shows as a card with "Remove" (drops the link only, the text stays). The two text fields stay editable. A link to a provider that is deleted or not on the device shows "A saved doctor that is no longer on the list" with Remove.
- Appointment detail: a "Saved doctor" block with the provider's name and contact links (and the address text when the place no longer holds it); a deleted provider shows only the copied text, no links.
- `.ics` export: `LOCATION` = the appointment's place completed with the linked provider's address on one line (not repeated when the place already holds it), and the provider's phone in the description.
- i18n: `locales/<lang>/providers.json` (en + pt-BR, typed in `catalogEn.ts`), `hub.entries.providers`, `appointments.detail.savedDoctor`, `settings.sync.entities.careProvider`.

## 5. Not done
- "Add to my doctors" from a Doctor-role member's self-declared professional profile: skipped. The profile is only exposed on `MemberDto.professional` for Doctor members and the members list is another feature's file (the Doctor dashboard worker is changing the same area); worth doing with it, as one button on the member row that opens `ProviderSheet` prefilled with name, specialty and registration number.
- No import of providers from past appointments, no duplicates check, no per-provider history of visits.
